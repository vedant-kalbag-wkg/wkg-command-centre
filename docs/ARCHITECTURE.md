# Architecture

A map of how `wkg-command-centre` is put together so a new developer can navigate the codebase and reason about request flow without reading every file. Pair this with [`DATABASE.md`](./DATABASE.md) for data-model detail and [`AZURE-SELF-HOSTING.md`](./AZURE-SELF-HOSTING.md) for the infra story.

> Local dev setup lives in [`DEVELOPMENT.md`](./DEVELOPMENT.md). Don't duplicate it here.

## TL;DR

- **Single Next.js 15 App Router app.** No microservices, no separate API server. Server Actions are the default mutation surface; HTTP route handlers exist only for things that *need* to be HTTP (auth callbacks, ETL cron entry, file exports).
- **One database.** Postgres, accessed via Drizzle ORM. Schema is a single file (`src/db/schema.ts`); migrations are SQL files generated by `drizzle-kit`.
- **Driver is portable.** `src/db/index.ts` auto-selects between `@neondatabase/serverless` (when the URL is `*.neon.tech`) and `postgres-js` (everything else). Self-hosted Postgres "just works" today; see DATABASE.md for the few places that leak.
- **Auth is Better Auth.** Invite-only, credentials provider, 30-day sliding sessions, role admin/member/viewer plus a `system` role used only by automation. RBAC is enforced inside server actions/layouts — there is no `middleware.ts`.
- **No edge runtime.** Every route handler that runs server code declares `runtime = "nodejs"`. Nothing in the app depends on Vercel-only platform features other than a single cron schedule, which already supports a bearer-token fallback.

## Stack

| Layer | Choice | Notes |
|---|---|---|
| Framework | Next.js 15 (App Router) | RSC + Server Actions; client components only where state demands it |
| Language | TypeScript (strict) | Module path alias `@/*` → `src/*` |
| ORM | Drizzle | Schema-first; `drizzle-kit` for migrations |
| DB driver | `postgres-js` (default) / `@neondatabase/serverless` (Neon hosts) | See `src/db/index.ts` |
| Auth | Better Auth + `@better-auth/drizzle-adapter` + `admin` plugin + `nextCookies` | Schema lives in `user` / `session` / `account` / `verification` tables |
| UI | Tailwind v4, base-ui, dnd-kit, react-big-calendar, svar Gantt, tanstack table | Brand tokens follow WeKnow Group guidelines |
| Test | Vitest (unit/integration), Playwright (E2E + UAT) | `playwright.config.ts` honours `PLAYWRIGHT_BASE_URL` for preview/prod runs |
| Hosting (today) | Vercel | Single cron at `0 4 * * *` → `/api/etl/azure/run` |
| DB hosting (today) | Neon Postgres (eu-west-2) | Pooled endpoint, `sslmode=require&channel_binding=require` |

## Runtime model

### Server Actions are the default mutation surface

Mutations live next to the page that triggers them in `actions.ts`. They:

1. Call `await auth.api.getSession(...)` (via a thin wrapper in `lib/auth.ts`).
2. Gate with `requireRole("admin"|"member"|...)` from `lib/rbac.ts`.
3. Apply scoping (e.g. `scoping/scoped-active-locations.ts`) for non-admins.
4. Mutate via Drizzle.
5. Write an `audit_logs` row.
6. Return a typed result; the client component does optimistic UI as needed.

There is no global middleware — gating is per action and per layout. The `(app)/layout.tsx` does the session check and the role-or-redirect.

### Route handlers (HTTP)

Only four exist:

| Route | Why it must be HTTP |
|---|---|
| `/api/auth/[...all]` | Better Auth's catch-all — sign-in, forgot-password, change-password, etc. |
| `/api/etl/azure/run` | Triggered by Vercel cron header **or** `x-etl-token: $ETL_SHARED_SECRET`. Returns 200/207/401/409/503. |
| `/api/export/excel` | Streams a generated xlsx — too large for Server Action JSON return |
| `/api/export/csv` | Same — streamed download |

All four declare `export const runtime = "nodejs"` (no edge). The ETL route also sets `maxDuration = 300` because blob enumeration can be slow.

### Auth model

- Better Auth with the `drizzleAdapter({ provider: "pg" })`. Tables: `user`, `session`, `account`, `verification` — all standard Better Auth shape.
- `disableSignUp: true` — invite-only is a **locked decision**. New users come in via the invite flow (which uses Better Auth's reset-password URL with `?invite=1`).
- Session: 30-day expiry, refreshed daily (sliding window).
- The `admin` plugin provides `defaultRole: "member"` and `adminRoles: ["admin"]`.
- A custom `userType` field (`internal` | `external`) lives on `user` and is surfaced on `session.user` so the portal can hard-gate external users out of internal routes. `input: false` keeps `userType` out of any signup payload — it's set at invite time only.
- A `system` role exists for ETL/automation and is **excluded** from `Role` union in `lib/rbac.ts` — it must never be granted to a real user.
- `nextCookies()` is the **last** plugin in the array — it has to wrap Server Action responses.

### RBAC roles

| Role | Effective surface |
|---|---|
| `admin` | Everything: settings, data import, user management, all analytics, all locations |
| `member` | App surface; analytics scoped by `user_scopes`; cannot manage users or import data |
| `viewer` | Read-only app surface; same scoping as member |
| `system` | ETL only — automation actor for sales imports. Never user-facing. |

`userType=external` overrides the role surface to portal-only views. Internal-only sensitive fields (commission, costs) are filtered server-side regardless of role when `userType=external`.

### Background work

| Job | How it runs today | Notes |
|---|---|---|
| Daily Azure sales ETL | Vercel cron `0 4 * * *` POSTs `/api/etl/azure/run` | `x-vercel-cron: 1` header **or** `x-etl-token` proves auth; gated by `ETL_AZURE_ENABLED=true` |
| Monday.com import | Operator-triggered in `/settings/data-import/monday` | Server action under `pg_try_advisory_lock` (key: import-specific constant) |
| Sales CSV import | Operator-triggered in `/settings/data-import/sales` | Stage → review → commit; staging table pruned 1d retention (#32) |
| Reset admin password | CLI: `scripts/reset-admin-password.ts` | Bypasses sign-up; documented in CLAUDE.md |

All long-running work uses Postgres advisory locks (`pg_try_advisory_lock`) so two operators clicking the same button or two cron runs overlapping is a 409, not data corruption.

## Request flow (cheat sheet)

```
Browser
  │  signed-in cookie (Better Auth session)
  ▼
Next.js (app router)
  │
  ├── (app)/layout.tsx ── auth.api.getSession() ── redirect /sign-in if missing
  │
  ├── Page (RSC) ── reads via Drizzle through `db` (auto-detected driver)
  │
  └── Form / button ── Server Action ── requireRole + scoping + audit + db
                         │
                         └── (rare) /api/auth/* via fetch — Better Auth handles
```

ETL flow:

```
Vercel cron / curl  ─POST→  /api/etl/azure/run
                              │  401 if neither x-vercel-cron nor x-etl-token
                              │  503 if ETL_AZURE_ENABLED!=true
                              ▼
                            runAzureEtl(db)
                              │  withAdvisoryLock(ETL_AZURE_LOCK_KEY) → 409 if held
                              │  for each region (with azureCode):
                              │    list blobs under {container}/{azureCode}/YYYY/MM/DD/*.csv
                              │    skip if already in sales_blob_ingestions (success)
                              │    AzureBlobSource.pull() → stage → commit
                              ▼
                            { processed[], skipped[], failed[] }  (200/207)
```

## Testing

- Unit + integration: `npm test` (vitest). Lots of `*.test.ts` colocated with code.
- E2E + UAT: `npm run test:e2e` (Playwright, headless). See [`tests/`](../tests) by domain (rbac, kiosks, sales, etc.).
- Remote/preview: `PLAYWRIGHT_BASE_URL=https://<preview> npx playwright test ...` runs against a live deployment instead of the local dev server. See CLAUDE.md for the Vercel git-branch alias rule.

## Things that are deliberately not in this codebase

- No background queue (BullMQ, Inngest, etc.) yet — Phase 8 will add Inngest for email send.
- No microservices.
- No GraphQL server (we *consume* Monday.com's GraphQL but don't expose one).
- No global Redis / cache layer — Postgres is the cache.
- No CDN config in repo — relies on Vercel's CDN today; on Azure, Front Door / CDN is opt-in.
