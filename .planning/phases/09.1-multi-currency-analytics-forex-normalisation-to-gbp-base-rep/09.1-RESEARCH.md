### Locked Decisions

**Rate source & ingest**
- D-01: Rate source = **Bank of England daily spot rate** (free, zero-auth, native GBP base).
- D-02: Daily fetch = **Inngest cron** `fx-rates.fetch-daily`, ~06:00 UTC, ordered before Azure sales ETL. Sales ETL is downstream — verifies the rate row exists for blob's `transaction_date` before stamping.
- D-03: Coverage = broad **BoE-supported set (~25 majors)**. CSV with unknown currency → ETL fails loudly; no silent GBP fallback.
- D-04: Backfill from earliest `transaction_date` to today. `currency='GBP'` rows = identity (no rate lookup).

**Missing-rate gap-fill**
- D-05: Routine non-publish (Mon–Fri pub, BoE skips weekends + UK bank holidays) = **carry-forward via lookup** (`WHERE rate_date <= transaction_date ORDER BY rate_date DESC LIMIT 1`). exchange_rates only stores publish-day rows.
- D-06: BoE fetch failure = **ingest with carry-forward + alert**. Sales keep flowing.
- D-07: **7-day staleness ceiling**. Beyond 7d → ETL hard-fails for that blob.
- D-08: Alerts via **Phase 8 `email_log` substrate**. Two new kinds: `fx_rate_fetch_failed` (cron) + `fx_rate_stale` (ETL).

**Companion column scope**
- D-09: **Only `net_amount_gbp`** added to `sales_records`. ROADMAP wording must be updated in this phase to drop vat/total mentions.

**Analytics UX continuity**
- D-10: **No user toggle.** Single-currency cohort → native; multi-currency cohort → GBP. Display follows data.
- D-11: Every aggregate query dual-emits `SUM(net_amount)` + `SUM(net_amount_gbp)` + `currency` resolved as `MIN(currency) WHEN COUNT(DISTINCT currency)=1 ELSE NULL`.
- D-12: Sorting / ranking / percentile **always uses GBP**. Display picks per D-10.
- D-13: Per-kiosk drill-down rows → native (single-currency by construction). No change to `format-currency.ts`.
- D-14: `classifyEligibleLocations:172` swaps `SUM(s.net_amount::numeric)` → `SUM(s.net_amount_gbp::numeric)`. POC email keeps `formatRevenueForKiosk` (native).
- D-15: `commission/processor.ts:206` commission base swaps to `net_amount_gbp`.
- D-16: `/admin/performance-alerts` always GBP + stale-rate banner when last successful BoE fetch > 24h ago.
- D-17: pivot-engine `net_amount` field keeps its name + ID for saved-pivot back-compat; underlying SQL rewrites per D-11; renderer auto-picks per D-10.

### Claude's Discretion (planner decides; recommendations below)

- Inngest cron exact minute → **recommend `0 6 * * *` UTC** (06:00 UTC = 06:00/07:00 BST). Weekly-poc-alerts uses `TZ=Europe/London`; for FX (a UK-bank publication) match BoE's London publishing tz with `TZ=Europe/London 0 6 * * *`.
- `numeric(p,s)` for `rate_to_gbp` → **recommend `numeric(18,10)`**. JPY rates run ~190 JPY/GBP → 1/190 = 0.0052631578…; 10 decimal places gives ~£0.00001 precision on a £100 transaction (well under 1 penny). Wider than `numeric(12,8)` to future-proof against very-low-value currencies (KRW, IDR).
- `source` column on `exchange_rates` → **recommend YES, default `'boe'`**. Cheap insurance; the deferred-ideas section explicitly anticipates a future NetSuite-as-source phase.
- Index on `sales_records.net_amount_gbp` → **recommend NO standalone index**. The existing `(location_id, transaction_date)` and `(region_id, transaction_date)` indexes already cover every analytics access pattern; SUM aggregates do not benefit from a value-column index. If a partial index is wanted, consider `WHERE net_amount_gbp IS NULL` for the backfill progress query — but drop after backfill completes.
- Backfill batching → **mirror existing 1k-chunk pattern** at `pipeline.ts:362–410`.
- Migration shape → **recommend split**: (a) `0046_phase_09_1_exchange_rates.sql` (table + indexes), (b) `0047_phase_09_1_sales_records_net_amount_gbp.sql` (column nullable + index), (c) `0048_phase_09_1_net_amount_gbp_not_null.sql` after backfill completes. Three small migrations are easier to review than one fat one and let the NOT NULL flip happen safely after the backfill script runs.
- Backfill = **one-shot script in `scripts/`**, not a Drizzle data-migration step. Mirrors `scripts/backfill-reversals.ts` and matches the pattern auto-memory `no_manual_sql_for_ops` warns against ONLY for recurring operator data ops — one-shot historical backfills are fine as scripts.
- Stale-rate banner placement → **inline at top of the page near `latestRunAt`**, reusing the same Card pattern at `src/app/(app)/admin/performance-alerts/page.tsx:23–30`.

### Pattern 1: Inngest cron with retries + step memoisation

**What:** Daily fetch with retries on Resend transient failures via Inngest's exponential backoff. Each step.run boundary is memoised across retries — fetch is cheap so re-run is fine; upsert is idempotent on `(currency, rate_date)`.

**When to use:** Every scheduled external-API fetch in this codebase.

**Example (mirrors `weekly-poc-alerts.ts:324–342`):**
```typescript
// Source: /src/inngest/functions/weekly-poc-alerts.ts (lines 324–342)
export const fxRatesFetchDailyFn = inngest.createFunction(
  {
    id: "fx-rates-fetch-daily",
    name: "FX rates daily fetch (BoE)",
    triggers: [{ cron: "TZ=Europe/London 0 6 * * *" }],
    concurrency: { limit: 1 },
    retries: 5,  // higher than POC alerts because BoE is the only source
  },
  async ({ step, runId }) => {
    const csv = await step.run("fetch-boe", async () => {
      const resp = await fetch(BOE_URL);
      if (!resp.ok) throw new Error(`BoE fetch HTTP ${resp.status}`);
      return await resp.text();
    });
    const rates = await step.run("parse-and-validate", async () => {
      return parseAndValidate(csv);  // returns Array<{currency, rateDate, rate}>
    });
    await step.run("upsert-rates", async () => {
      await db.insert(exchangeRates).values(rates).onConflictDoNothing({
        target: [exchangeRates.currency, exchangeRates.rateDate],
      });
    });
  },
);
```

### Pattern 2: Carry-forward rate lookup

**What:** Standard finance carry-forward. For a transaction date, find the most recent published rate ≤ that date.

**When to use:** Every site that needs a per-currency-per-date rate.

**Example:**
```typescript
// Source: D-05 in CONTEXT.md; standard finance pattern
export async function getRateForDate(
  currency: string,
  date: string,  // ISO 'YYYY-MM-DD'
): Promise<{ rate: number; rateDate: string; staleDays: number } | null> {
  if (currency === 'GBP') return { rate: 1.0, rateDate: date, staleDays: 0 };
  const [row] = await db
    .select({ rate: exchangeRates.rateToGbp, rateDate: exchangeRates.rateDate })
    .from(exchangeRates)
    .where(and(eq(exchangeRates.currency, currency), lte(exchangeRates.rateDate, date)))
    .orderBy(desc(exchangeRates.rateDate))
    .limit(1);
  if (!row) return null;
  const staleDays = Math.floor((Date.parse(date) - Date.parse(row.rateDate)) / 86400000);
  return { rate: Number(row.rate), rateDate: row.rateDate, staleDays };
}
```

### Anti-Patterns to Avoid

- **Re-stamping `net_amount_gbp` retroactively** when BoE issues a rate revision. CONTEXT.md (deferred ideas, "BoE rate-revision back-stamping") is explicit: locked-at-ingest. The reconciliation contract IS that historical reports do not change.
- **Silent fallback to GBP for unknown currency code in CSV**. D-03 says hard-fail. A row with `currency='ZWL'` (Zimbabwe Dollar) when our supported set excludes it should fail the ETL blob with a clear error, not silently treat it as GBP.
- **A single fat migration adding table + column + NOT NULL**. The NOT NULL must come AFTER the backfill, otherwise you cannot apply the migration. Split into 0046 / 0047 / 0048 (or similar) so the apply order is explicit.
- **Using `formatCurrency` from `formatters.ts` for native cells**. It is hard-coded GBP. Either extend it to take a ccy param or reuse `formatRevenueForKiosk`.
- **A `vat_amount_gbp` or `total_amount_gbp` column** "for completeness" — D-09 explicitly forbids these.
- **A user-facing currency toggle** — D-10 explicitly forbids.
- **Daily cron writing carry-forward rows** for non-publish dates — D-05 says lookup-time carry-forward only. Cron writes only ~5 rows per currency per week.

## Common Pitfalls

### Pitfall 1: BoE non-publish date confusion (weekend / bank holiday)

**What goes wrong:** A new dev assumes BoE publishes daily and writes a cron that hard-fails on Saturday because no row was returned.
**Why:** BoE only publishes Mon–Fri, and skips UK bank holidays. CSV download for a weekend date returns headers only.
**How to avoid:** D-05 carry-forward via lookup. The cron's "fetch failed" alert is gated on a real HTTP-level failure (5xx, timeout, parse error), not on "today's row missing."
**Warning signs:** `fx_rate_fetch_failed` emails firing on every Saturday/Sunday → cron is treating empty response as failure.

### Pitfall 2: Lockfile drift from a new HTTP / XML parser dep

**What goes wrong:** Plan adds `xml2js` (or `axios`, or `papaparse`) → `npm install` on macOS → CI fails on Linux with `Missing: @emnapi/...` — exactly the failure shape CLAUDE.md catalogues.
**Why:** macOS-arm64 lockfile excludes wasm32-wasi binding tree; CI Linux x64 needs it.
**How to avoid:** Stick with native `fetch` + native CSV split. If a parser dep is unavoidable, regen lockfile via the CLAUDE.md Docker `--platform linux/amd64` flow.
**Warning signs:** Local `npm ci --dry-run` clean, CI red with `Missing: @emnapi/*`.

### Pitfall 3: Stamping `net_amount_gbp` BEFORE the rate is known to exist

**What goes wrong:** A blob lands at midnight (Saturday transaction); ETL runs at 06:00 UTC Sunday; BoE has no Saturday or Sunday row; ETL stamps from the previous published Friday rate — fine, that is D-05 carry-forward. But if the cron has been broken for 8 days and the carry-forward exceeds 7 days, the blob commits anyway with a stale rate.
**Why:** Carry-forward is unbounded unless the staleness ceiling is enforced **at the per-row stamp**, not just on a periodic check.
**How to avoid:** `getRateForDate` returns `staleDays`; ETL checks `staleDays > 7` per row and refuses the blob. Then emits `fx_rate_stale`.
**Warning signs:** A `net_amount_gbp` value derived from a rate > 7d older than the row's `transaction_date`. Add an integration test that asserts this invariant.

### Pitfall 4: Pivot-engine field rename breaks saved pivots

**What goes wrong:** Plan renames pivot-engine `net_amount` → `net_amount_gbp`. Every saved pivot row in the DB references the old field id. Users open their saved pivots and get blank cells.
**Why:** Field IDs are stored in the saved-pivot JSON.
**How to avoid:** D-17 says **keep the name**. Rewrite the underlying SQL only. The renderer auto-picks per D-10.
**Warning signs:** Validation tests that load a saved pivot row from before the change must still resolve to a non-empty cell.

### Pitfall 5: `formatCurrency` is hardcoded GBP

**What goes wrong:** Plan dual-emits `(native, gbp, ccy_key)`, renderer reads `currency_key`, picks "native" path, calls `formatCurrency(value)` — and renders a EUR amount as "£42.00".
**Why:** `formatters.ts:5` instantiates a single GBP-pinned `Intl.NumberFormat` at module load.
**How to avoid:** Add `formatNativeCurrency(value: number, currency: string): string` to `formatters.ts` (mirrors `formatRevenueForKiosk` shape but with the analytics fallback). Or import + reuse `formatRevenueForKiosk` directly.
**Warning signs:** Visual review of any analytics page showing a non-GBP cohort renders the wrong symbol.

### Pitfall 6: `is_weknow_fee` filter discrimination forgotten in dual-emit

**What goes wrong:** Plan dual-emits Sales mode (`SUM(net_amount) FILTER (WHERE NOT is_weknow_fee)`) but forgets to dual-emit Revenue mode (`SUM(net_amount) FILTER (WHERE is_weknow_fee)`). Half the analytics surface stays GBP-broken.
**Why:** Both modes aggregate `net_amount`; only the filter differs. Easy to scan one mode and miss the other.
**How to avoid:** The audit table below explicitly lists both `amountMode` (Sales mode predicate) and unfiltered SUMs. Both must dual-emit per D-11. Tooltip update at `region-metrics.tsx:33` is in scope per D-10.
**Warning signs:** Switching from Sales mode to Revenue mode on a multi-currency cohort shows the cohort flipping back to native rendering — a sign one mode dual-emits and the other doesn't.

### Pitfall 7: Re-stamping during the migration window (NOT NULL flip)

**What goes wrong:** Migration 0048 sets `net_amount_gbp NOT NULL` while the backfill script is still running on a large historical corpus. The migration locks the table; backfill stalls; deploy times out.
**Why:** Backfill on a corpus of N rows takes time; the NOT NULL flip needs all N rows populated first.
**How to avoid:** Sequence: (1) migration 0046 + 0047 land + deploy, (2) backfill script runs to completion in a separate operator action, (3) `SELECT COUNT(*) FROM sales_records WHERE net_amount_gbp IS NULL` returns 0, (4) only THEN apply migration 0048.
**Warning signs:** Migration 0048 in the same plan as 0046/0047 with no operator-gated step between.

### Pitfall 8: `email_log.kind` enum drift between TypeScript and DB

**What goes wrong:** Plan extends `EmailKind` union in TypeScript only; production has a code path that writes a kind not in the union — but there is no DB constraint, so it silently lands.
**Why:** `email_log.kind` has no CHECK constraint (verified by grep — only `email_log_status_check` exists, on `status`).
**How to avoid:** Either (a) accept the TypeScript-only enforcement, OR (b) add a kind CHECK constraint in migration 0046+. **Recommendation:** match the existing pattern (kind is enum-only at TS) for back-compat. Document this is intentional.
**Warning signs:** A `email_log` row with a kind that no template/event references — orphan kind drift.

### One-shot backfill (mirrors `scripts/backfill-reversals.ts`)

```typescript
// Source: pattern mirrors scripts/backfill-reversals.ts:1–60
// Run: npx tsx --env-file=.env.neon-dev scripts/backfill-net-amount-gbp.ts [--dry-run]
async function main() {
  const url = process.env.DATABASE_URL;
  if (!url) throw new Error("DATABASE_URL not set");
  const pool = new Pool({ connectionString: url });
  const client = await pool.connect();
  const CHUNK = 1000;
  let cursor: string | null = null;  // (transaction_date, id) tuple cursor
  while (true) {
    const rows = await fetchNextChunk(client, cursor, CHUNK);  // WHERE net_amount_gbp IS NULL
    if (rows.length === 0) break;
    const updates = rows.map(r => ({
      id: r.id,
      net_amount_gbp: r.currency === 'GBP'
        ? r.net_amount  // identity
        : (Number(r.net_amount) * lookupRate(r.currency, r.transaction_date)).toFixed(2),
    }));
    await applyChunk(client, updates);
    cursor = rows[rows.length - 1].cursor_key;
  }
}
```

## Open Questions

1. **Does the BoE CSV download URL paginate or stream?**
   - What we know: CSV download is documented as a single-shot HTTP response.
   - What's unclear: For a multi-year backfill request (Datefrom/Dateto spanning 2 years), does it return the full payload in one response?
   - Recommendation: For the daily cron, only fetch today's rates (single date) — payload is tiny. For the historical backfill of `exchange_rates`, fetch year-by-year ranges in the backfill script. Test the largest single response (~25 currencies × 1 year = ~6500 cells) is well-formed before production deploy.

2. **Does NetSuite assign a transaction_date in a different timezone than BoE's London publish-day?**
   - What we know: BoE publishes rates at end of London business day (~16:00 GMT/BST).
   - What's unclear: A NetSuite transaction at 23:00 NYC on `2026-05-09` — is `transaction_date` recorded as `2026-05-09` (NYC date) or `2026-05-10` (London date)?
   - Risk: A row with `transaction_date='2026-05-09'` looks up the rate for that date, but BoE rates for `2026-05-09` weren't published yet at 23:00 NYC (which is 04:00 London on `2026-05-10`).
   - Recommendation: Phase 9.1 IS NOT solving this — D-05 carry-forward inherently handles "rate not yet published for this date" as a 1-day-stale lookup. Document this as a known approximation.

3. **Should the `fx_rate_stale` email be admin-only, or also POC-routed?**
   - What we know: D-08 says "alert ops" via email_log.
   - What's unclear: Does this go to one global admin address, or fan out per-region the way POC alerts do?
   - Recommendation: Single admin address (e.g., `vedant.kalbag@weknowgroup.com` per memory `prod-admin-account`) — `fx_rate_stale` is an infra alert, not a per-POC business signal. Plan should add a `FX_ALERT_TO` env var (or hard-code the admin email per the existing prod-admin pattern).

## Risks & Open Questions

### Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| BoE CSV format changes (column order / new column / removed series) | LOW (gov-stable) | HIGH (cron parses wrong row) | Zod-validate the parsed shape; cron emits `fx_rate_fetch_failed` on validation error → human investigates within carry-forward window |
| BoE outage > 7 days | LOW | HIGH (sales ETL hard-fails) | D-07 by design; the loud failure IS the mitigation. Operator can manually insert a carry-forward row into `exchange_rates` to unblock. |
| Backfill script runs out of memory on large historical corpus | MEDIUM | MEDIUM (operator restarts; cursor-based so resumable) | Cursor-based pagination per chunk + script is idempotent (`WHERE net_amount_gbp IS NULL`); restartable |
| Migration 0048 (NOT NULL flip) applied before backfill completes | MEDIUM (deploy automation) | HIGH (deploy stalls / table locks) | **Sequence enforced in plans:** 0046+0047 in one plan; backfill in a separate plan with explicit operator-gated step; 0048 in a third plan |
| `formatCurrency` GBP-pinning silently corrupts native cells | HIGH (it WILL break if not addressed) | MEDIUM (visual bug, not data bug) | Add `formatNativeCurrency(value, ccy)` in same plan as the renderer dispatch (FX-03b). Playwright E2E covers regression. |
| Lockfile drift if a parser dep is added on macOS | MEDIUM | HIGH (CI red) | Stick with native fetch + CSV split. If unavoidable, follow CLAUDE.md Docker `--platform linux/amd64` regen. |
| Saved-pivot regression (D-17 violated) | LOW (researcher flagged it) | HIGH (UI broken for power users) | Pivot-engine test must assert field name `net_amount` still resolves; landed in FX-03b plan |
| Phase 9 POC email regression (native lost) | LOW | MEDIUM | `format-currency.test.ts` already exists; extend with explicit "native preserved post-FX swap" assertion |
| Pivot-engine `formatCell` (line 349) is GBP-only via `formatCurrency` | HIGH | MEDIUM | Plan FX-03b must extend `formatCell` to take a currency param OR dispatch on the row's currency_key |
