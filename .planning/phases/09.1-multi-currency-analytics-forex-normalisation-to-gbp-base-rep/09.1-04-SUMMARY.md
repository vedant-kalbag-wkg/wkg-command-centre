## Decisions Made

- **Move the Wave 0 RED test instead of extending the integration glob.** Two paths satisfied the routing problem (move file vs. extend `vitest.config.ts` integration include to cover `src/**/*.integration.test.ts`). The RED-stage test header explicitly preferred option (a). Move keeps integration tests in one directory tree and matches the existing analog (`tests/admin/performance-alerts.integration.test.ts`).
- **`step.sendEvent` over `inngest.send` for fan-out.** PATTERNS shared pattern 6 documents the wire — `weekly-poc-alerts.ts:280-297` does `step.sendEvent("emit-skip-rows", [...])`. Using `step.*` ensures Inngest memoises the dispatch within the run; on retry the alert is replayed from step state, not re-emitted. The RED test's mock surface (`inngest.send`) was wrong; fixed by routing the step-shim's `sendEvent` into the same recorder.
- **Catch fetch errors at the handler boundary, not inside `step.run("fetch-boe", ...)`.** Inngest discards step state on throw; if the alert event were emitted from inside the same `step.run` that throws, the alert would be wiped on retry-5 (the operator-facing final attempt). Catching at the handler boundary lets us fire `step.sendEvent` first (which Inngest persists as a separate step), then re-throw.
- **Stub `inngest.createFunction` in the test mock.** SUT calls `inngest.createFunction(config, handler)` at module top-level for the cron registration. The Wave 0 test only exercises `_handleFxRatesFetchDaily`, but the top-level call still runs at import time. A no-op stub (`(config, _handler) => config`) lets the import succeed without the real Inngest client. Lower-friction than skipping the registration export inside a test branch.
- **`mockImplementation` over `mockResolvedValue` for `fetch`.** `mockResolvedValue` returns the same Response instance every call. `Response.text()` consumes the body, so the idempotency test's second `_handleFxRatesFetchDaily` call would throw `Body is unusable: Body has already been read`. `mockImplementation(async () => new Response(...))` constructs a fresh Response per call.
- **`payloadHash` on the fan-out.** `fx_rate_fetch_failed:${isoDate}:${runId}` deduplicates the alert across Inngest retry replays via the partial unique idx on `email_log.(kind, payload_hash) WHERE payload_hash IS NOT NULL` (migration 0041, used by Phase 8 send-email). Without it, retry-5 of a real outage would write 5 email_log rows + send 5 emails.
- **`retries: 5` over `retries: 3`.** RESEARCH § Code Examples calls this out: BoE is the only rate source, so a transient outage benefits from more attempts before paging ops. POC alerts have implicit retry via the next Monday's cron; FX has no such buffer beyond the carry-forward window.
- **`source: "boe" as const` in the upsert values.** The schema column defaults to `"boe"` already (D-02), so omitting it would work — but spelling it out keeps the source-of-truth at the call site, so a future NetSuite-as-source phase that adds `source: "netsuite"` to a parallel cron doesn't need to discover the default's value.
