## Accomplishments

- **Gap 1 closed at runtime:** `template === "plain-text"` sentinel branch in `send-email.ts` resolves both `fx_rate_fetch_failed` (Inngest cron) and `fx_rate_stale` (Azure ETL per-blob gate) to hand-crafted text bodies → `Resend.emails.send` is invoked. - **CR-01 / WR-04 closed:** All 4 `sql.raw` UUID-IN-list interpolations under `src/lib/analytics/queries/` are replaced with parameter-safe Drizzle helpers (`inArray()` for direct column filters, `sql.param(ids)::uuid[]` + `= ANY(...)` for the EXISTS subquery shapes). Centralised `src/lib/uuid.ts` validator gates URL `searchParams` ids at every page-level entrypoint (regions, hotel-groups, location-groups) before they reach the SQL builder. SQL-injection probe spec confirms the drizzle pg adapter throws on uuid bind-cast for any non-UUID slip-through.
- **CR-02 closed:** `getFxAlertRecipient()` in `src/lib/fx/alert-recipient.ts` is the single source of truth for the FX alert recipient. Both fan-out call sites import it; both literal `?? "vedant.kalbag@weknowgroup.com"` fallbacks are removed. Missing `FX_ALERT_TO` throws a descriptive deploy-time error rather than silently routing to the prod admin's personal inbox. `.env.example` documents the env var as REQUIRED.
- **CR-03 closed:** `src/lib/analytics/queries/hotel-groups.ts` now imports `buildActiveLocationCondition` from `@/lib/analytics/active-locations` (matching every other analytics query), with the local variable renamed `exclusionCondition → activeLocationCondition`. ## Decisions Made

1. **Legacy `buildExclusionCondition` alias retained with `@deprecated` JSDoc rather than deleted in-plan.** Plan Step 6 explicitly listed the fallback policy: if external callers exist outside `shared.ts`, leave the alias and add a deprecation comment with caller-list inventory. Grep across `src/` + `tests/` showed 7 callers (commission/where-builder.ts + 6 unit-test mocks). A clean delete would have required migrating where-builder.ts + rewriting 6 test mocks — out of scope for the gap-closure plan, and a future plan can do it cleanly.
2. **Plain-text branch as a `template === "plain-text"` sentinel rather than adding entries to TEMPLATES.** Keeps TEMPLATES focused on React-component templates; future plain-text kinds (digests, capacity warnings) extend the sentinel branch only. Documented inline in send-email.ts.
3. **Page-level `isUuid` filter silently drops bad ids to empty selection.** Throws would surface stack-shaped errors to the user for a malformed URL; the existing `EmptyState` UX is already the right rendering for "no selection". Documented inline in each page.tsx.
4. **`getFxAlertRecipient()` throws at call site rather than at module load.** Helper is only invoked on the failure path, so a deploy with `FX_ALERT_TO` unset still boots; the loud throw fires the first time an alert path actually tries to fire. Avoids breaking unrelated app surfaces if the env var is missing.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 — Blocking] Mock factory in `tests/inngest/send-email-fx-dispatch.integration.test.ts` used arrow function which can't be a constructor**

- **Found during:** Task 1 (running the new integration test)
- **Issue:** Initial test wrote `Resend: vi.fn(() => ({ emails: { send: mockSend } }))` per the plan's example. The runtime SUT does `new Resend(...)`, and arrow functions cannot be invoked with `new` → `TypeError: () => ... is not a constructor`.
- **Fix:** Switched the mock factory to `Resend: vi.fn(function () { return { emails: { send: mockSend } }; })` to match the existing `tests/email/send-email-fn.integration.test.ts` shape.
- **Files modified:** `tests/inngest/send-email-fx-dispatch.integration.test.ts`
- **Verification:** All 3 specs in the new test now PASS.
- **Committed in:** fbb7d8b (Task 1 commit)

**2. [Rule 3 — Blocking] `hotel-groups.test.ts` regression suite would have failed without an active-locations mock after CR-03 migration**

- **Found during:** Task 3 planning (analysing the impact of changing the import from `@/lib/analytics/queries/shared` to `@/lib/analytics/active-locations`)
- **Issue:** Existing `hotel-groups.test.ts` mocks `buildExclusionCondition` from `shared` and asserts `mockExecute` is called exactly twice. After CR-03 migration, `buildHotelGroupWhere` calls `buildActiveLocationCondition()` from `active-locations.ts`, which in turn calls `executeRows` on `db` → adds an extra `db.execute` call → breaks the assertion.
- **Fix:** Added a `vi.mock("@/lib/analytics/active-locations", ...)` block to `hotel-groups.test.ts` mirroring the exact shape already in `regions.test.ts:35-41` (mocks `getActiveLocationIds`, `buildActiveLocationCondition`, `buildActiveLocationConditionForRawContext` to short-circuit the DB lookup).
- **Files modified:** `src/lib/analytics/queries/hotel-groups.test.ts`
- **Verification:** `npx vitest run src/lib/analytics/queries/hotel-groups.test.ts` → 6/0 GREEN.
- **Committed in:** c49a4f5 (Task 3 commit)
