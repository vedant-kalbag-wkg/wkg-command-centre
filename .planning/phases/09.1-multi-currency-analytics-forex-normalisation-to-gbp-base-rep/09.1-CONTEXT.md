# Phase 9.1: Multi-currency analytics — forex normalisation to GBP base reporting - Context

**Gathered:** 2026-05-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Cross-currency portfolios rank correctly. The phase introduces forex
normalisation by stamping every `sales_records` row with a GBP companion
column at ingest, switching the Phase 9 POC underperformance classifier
to GBP-normalised revenue for percentile ranking, and audit-swapping
every analytics aggregate that today does `SUM(net_amount)` across
mixed-currency rows.

### In scope
- New `exchange_rates(currency, rate_date, rate_to_gbp, …)` table,
  populated daily from Bank of England spot rates via an Inngest cron
  ordered before the existing Azure sales ETL.
- New `sales_records.net_amount_gbp` column (numeric(12,2)), populated
  at ingest using the BoE rate for the row's `transaction_date`. Rate
  is locked at insert time — later BoE revisions do not retroactively
  rewrite stamped rows (idempotency + reconciliation auditability).
- Backfill of `exchange_rates` from earliest `transaction_date` in
  `sales_records` to today; backfill of `sales_records.net_amount_gbp`
  for every existing row using the rate for its own `transaction_date`.
- Analytics audit + swap: every `SUM(net_amount)` site is updated to
  return BOTH `SUM(net_amount)` (native) and `SUM(net_amount_gbp)`
  (GBP), plus a `currency` key indicating single-currency vs mixed.
  Sorting and ranking always use GBP. Display picks native when the
  cohort is single-currency, GBP when mixed.
- `classifyEligibleLocations` switches its percentile rank to
  `SUM(net_amount_gbp)` (cross-portfolio is always multi-currency by
  definition).
- `commission/processor.ts` switches its commission base to
  `SUM(net_amount_gbp)` (commission is paid out in GBP regardless of
  source currency).
- `/admin/performance-alerts` dashboard always displays GBP (cross-
  portfolio surface).
- Email alert kinds for FX-fetch failure and stale-rate ceiling, on the
  Phase 8 `email_log` substrate.
- ROADMAP + REQUIREMENTS edits to (a) update Phase 9.1's column scope
  to `net_amount_gbp` only (drop the `vat_amount_gbp` /
  `total_amount_gbp` listing — see D-09), (b) lock the rate source as
  BoE (no longer "TBD"), and (c) draft the FX-01..FX-04 requirement
  series.

### Out of scope (other phases / deferred)
- `vat_amount_gbp`, `total_amount_gbp` companion columns — only add when
  there is a real analytics consumer. None today.
- Per-kiosk POC email rendering changes — already correct (Phase 9
  `format-currency.ts` shows native currency by design; this phase does
  not touch it).
- Multi-source rate strategies (BoE + ECB cross-check, NetSuite-as-
  source-of-truth for finance reconciliation) — single source for v1.1.
- Per-currency historical rate revisions / re-stamping when BoE issues
  corrections — locked-at-ingest is the explicit intent.
- A user-facing native↔GBP toggle — display follows the data, no
  switch (D-10).

</domain>

<decisions>
## Implementation Decisions

### Rate source & ingest
- **D-01:** Rate source is the **Bank of England daily spot rate**.
  Native GBP base (no triangulation through EUR), free, zero-auth,
  public dataset. Covers the major currencies our outlets actually
  book in. ECB and NetSuite-as-source were considered and rejected:
  ECB pivots through EUR (avoidable triangulation error); NetSuite
  couples ETL to vendor auth + rate limits without a current
  reconciliation requirement from Finance.

- **D-02:** Daily rate fetch is an **Inngest cron** (function name
  `fx-rates.fetch-daily`), reusing the Phase 8/9 Inngest substrate.
  Schedule ~06:00 UTC (planner's exact-minute discretion), explicitly
  ordered **before** the existing Azure sales ETL. Sales ETL becomes
  downstream — it verifies the rate row(s) needed for the blob's
  `transaction_date` exist before stamping `net_amount_gbp`.

- **D-03:** Currency coverage is the **broad BoE-supported set**
  (~25 majors: GBP, EUR, USD, AUD, CAD, JPY, CHF, …). The cron pulls
  every BoE-listed currency daily. An incoming CSV row with a currency
  outside the supported set causes the sales ETL to **fail loudly with
  a clear error** so an admin extends the supported set explicitly.
  No silent fallbacks to GBP for unknown codes.

- **D-04:** **Backfill `exchange_rates` from earliest `transaction_date`
  in `sales_records` to today.** True historical normalisation: every
  existing row gets a `net_amount_gbp` computed against the BoE rate
  for its own `transaction_date`. Rows where `currency = 'GBP'` are
  the identity case — set `net_amount_gbp = net_amount` directly with
  no rate lookup (cheaper backfill, no dependency on
  `exchange_rates` for the GBP majority).

### Missing-rate gap-fill
- **D-05:** Routine non-publish dates (BoE only publishes Mon–Fri,
  skips UK bank holidays) are handled by **carry-forward via lookup**.
  `exchange_rates` only stores rows on real publish dates. Lookup is
  `SELECT rate_to_gbp FROM exchange_rates WHERE currency = ? AND
  rate_date <= transaction_date ORDER BY rate_date DESC LIMIT 1`.
  Standard finance practice; cron writes only ~5 rows per currency per
  week.

- **D-06:** When the daily BoE fetch **fails** (network, BoE down,
  parse error) and there's no rate row for today, sales ETL
  **falls back to the last known rate via carry-forward**, stamps
  `net_amount_gbp` using that, and emits an alert. Sales keep flowing
  during BoE outages. Once tomorrow's fetch succeeds, no automatic
  re-stamping — D-07 sets the staleness ceiling for when this stops
  being acceptable.

- **D-07:** **7-day staleness ceiling.** If the most recent
  `rate_date` for a currency is more than 7 calendar days older than
  the row's `transaction_date`, the sales ETL **hard-fails** for that
  blob and refuses to commit. Loud signal that the data pipeline is
  broken, not just a long weekend. Beyond the ceiling, no `*_gbp`
  stamp is produced.

- **D-08:** Alerts fire via the **Phase 8 `email_log` substrate**.
  Two new email kinds:
  - `fx_rate_fetch_failed` — emitted by the Inngest cron when BoE
    fetch errors. Contains last-known fetch timestamp + retry next
    cycle hint.
  - `fx_rate_stale` — emitted by sales ETL when carry-forward exceeds
    the 7-day ceiling. Contains the affected currency, last-known
    `rate_date`, and the blob being blocked.
  Reuses Resend transport, idempotency hash, retention. No Inngest-
  dashboard-only alerts — admin must see this in email.

### Companion column scope
- **D-09:** Add **only `net_amount_gbp`** to `sales_records`
  (numeric(12,2), nullable until backfill completes, then NOT NULL).
  Issue #39 spec; ROADMAP wording will be updated in this phase to
  match (drop the `vat_amount_gbp` and `total_amount_gbp` listing).
  Rationale:
  - Every analytics query today aggregates `net_amount`. None aggregate
    `vat_amount` or a synthetic `total_amount` cross-currency.
  - `gross_amount`/`total_amount` was dropped in the 2026-04-24
    NetSuite ETL rewrite — there is no source `total_amount` to
    convert. A `total_amount_gbp` column would be a derived
    denormalisation (`net_gbp + vat_gbp`) that introduces drift risk
    for zero current value.
  - Adding more companion columns is cheap when an actual consumer
    appears — defer until then.

### Analytics UX continuity
- **D-10:** **No user-facing native↔GBP toggle.** The data drives the
  display. Rule:
  - **Single-currency cohort** (`COUNT(DISTINCT currency) = 1` over
    the aggregate group) → display the native sum
    (`SUM(net_amount)`) with that currency's symbol.
  - **Multi-currency cohort** (`COUNT(DISTINCT currency) > 1`) →
    display the GBP sum (`SUM(net_amount_gbp)`) with `£`.

- **D-11:** **Every aggregate query computes BOTH** `SUM(net_amount)`
  (native) and `SUM(net_amount_gbp)` (GBP), plus a `currency` field
  resolved as `MIN(currency) FILTER (WHERE …) WHEN
  COUNT(DISTINCT currency) = 1 ELSE NULL` (or equivalent). Renderer
  reads the `currency` field and picks which sum to show.

- **D-12:** **Sorting / ranking / percentile across cohorts always
  uses GBP** (`net_amount_gbp`). Display is independent of compute. So
  a EUR-only region and a GBP-only region rank correctly against each
  other in the same view; each shows its own native total in its row.

- **D-13:** **Per-kiosk drill-down rows** (single kiosk, definitionally
  single currency) → native, matching the existing Phase 9 POC email
  contract via `src/lib/performance-alerts/format-currency.ts`. No
  change to that file.

- **D-14:** `classifyEligibleLocations` (`src/lib/performance-alerts/
  classify-locations.ts:172`) swaps `SUM(s.net_amount::numeric)` →
  `SUM(s.net_amount_gbp::numeric)`. Cross-portfolio is always
  multi-currency by definition; ranking always GBP. POC email continues
  to render native via the existing `formatRevenueForKiosk` helper.

- **D-15:** `commission/processor.ts` switches its commission base
  (lines 75–241, the `SUM(netAmount) WHERE isWeknowFee=true`
  computation) to `net_amount_gbp`. Commission is paid out in GBP
  regardless of source currency, so the base is always GBP-normalised.

- **D-16:** `/admin/performance-alerts` always displays GBP (cross-
  portfolio surface). Stale-rate banner: surface a small inline
  indicator when the last successful BoE fetch is older than 24h
  (planner's exact threshold + placement discretion; reuse the
  page's existing "last run" data block pattern).

- **D-17:** The pivot engine field today named `net_amount` in
  `pivot-engine.ts` (line 68) keeps its name and ID for backward
  compatibility with saved pivots, but its underlying SQL is rewritten
  per D-11 (returns both native + GBP columns + currency key). Display
  label remains `Revenue` / `Sales` per existing Sales/Revenue mode
  filter (`is_weknow_fee` in / out). The auto-pick rule (D-10) drives
  cell rendering — no schema change to saved-pivot rows.

### Schema additions (consolidated)
- `exchange_rates(currency text, rate_date date, rate_to_gbp
  numeric(p,s), source text default 'boe', fetched_at timestamptz,
  primary key (currency, rate_date))`. Precision/scale of `rate_to_gbp`
  is Claude's discretion — JPY rates need ~6+ decimal places; planner
  picks numeric(12,8) or similar.
- `sales_records.net_amount_gbp numeric(12,2)` — populated at ingest
  per D-04/D-05/D-06. Index? Planner's call (likely yes, on at least
  `(location_id, transaction_date)` for the existing analytics access
  patterns).
- New email kinds in `email_log.kind` check constraint:
  `fx_rate_fetch_failed`, `fx_rate_stale`. Migration extends the
  existing constraint set (last similar migration: 0044).
- Migration shape: planner's discretion on splitting (single
  migration adding both table + column + indexes, vs three migrations
  for table / column / NOT NULL). Migration numbers start at
  **0046+** (last migration is `0045_phase_09_hotel_alerts.sql`).

### Claude's Discretion
- Exact Inngest cron minute (06:00 UTC is a sensible default but any
  pre-Azure-ETL slot is fine).
- `numeric(p, s)` precision/scale for `exchange_rates.rate_to_gbp`.
- Whether the `source` column on `exchange_rates` is worth adding now
  vs deferring (cheap insurance for future multi-source; trivial schema
  cost).
- Index strategy on `sales_records.net_amount_gbp`.
- Backfill batching strategy (chunk size, transaction boundaries) —
  the existing Azure ETL pattern handles 1k chunks; planner mirrors.
- The `<spec_lock>` mechanic is unused for this phase (no SPEC.md
  was authored before discuss-phase) — researcher and planner
  agents read this CONTEXT.md as the design contract directly.
- Exact placement of the stale-rate indicator on
  `/admin/performance-alerts`.
- Whether the FX backfill runs as part of the migration (Drizzle data-
  migration step) or a one-shot script invoked once after deploy.

<specifics>
## Specific Ideas

- **No user-facing toggle.** D-10 was explicit: "If the data being
  aggregated has multiple currencies, I want it all reported in GBP.
  If the data only has a single currency, then it is to be displayed
  in native currency. This is dependent on the data being selected —
  we don't need a switch for the user."
- **Native = honest, GBP = comparable.** The hybrid is intentional:
  per-kiosk and per-region drill-downs in their own currency keep the
  numbers operationally meaningful (a French POC sees €), while every
  cross-cohort aggregate reports in £ so portfolios rank correctly.
- **Locked-at-ingest rate.** `net_amount_gbp` is computed once at
  insert time and never retroactively rewritten when BoE issues a
  rate revision. Keeps historical reports stable + reconcilable.
- **Sales vs Revenue mode** (per the existing tooltip at
  `region-metrics.tsx:33`) BOTH need the swap. Both filter `net_amount`
  by `is_weknow_fee` differently; both must dual-emit native + GBP +
  currency-key.

</specifics>
