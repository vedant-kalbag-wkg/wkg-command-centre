# Phase 9.1: Code Review Report

**Reviewed:** 2026-05-10
**Depth:** standard
**Files Reviewed:** 62
**Status:** issues_found

## Summary

Phase 9.1 implements multi-currency forex normalisation: BoE daily rate fetch (Inngest cron), `exchange_rates` table, `sales_records.net_amount_gbp` stamping at ETL + backfill, and dual-emit native+GBP analytics with renderer dispatch (D-10/D-11/D-12).

Forex semantics are correctly implemented (BoE foreign-per-GBP → divide; D-04 GBP identity short-circuit; D-05 carry-forward; D-07 staleDays > 7 ceiling). Migration ordering is sound (0047 NULLABLE → backfill → 0048 NOT NULL with idempotent guard). Pivot-engine field-id preservation per D-17 is intact. POC email native formatter (`format-currency.ts`) is correctly untouched — `formatNativeCurrency` was added as a new sibling to `formatCurrency` in `src/lib/analytics/formatters.ts`.

However, several BLOCKER-class defects were found:

1. **SQL injection vectors** in `regions.ts` and `location-groups.ts` (and pre-existing in `hotel-groups.ts`). Phase 9.1 inherited these patterns when adding GBP columns and did not fix them. While inputs are server-action-supplied UUIDs, the attack surface is real if filter shape ever loosens.
2. **Hotel-groups query did not migrate to `buildActiveLocationCondition`** — still calls `buildExclusionCondition` (alias), inconsistent with the rest of the analytics surface and missing the active-locations performance fix.
3. **Hardcoded production email recipient** as fallback in two cron paths.
4. **DST-affected staleness arithmetic** in `getRateForDate` and the backfill script will under-count `staleDays` by 1 across a UK DST transition, allowing rates 1 day past the 7-day ceiling to slip through.
5. **Backfill chunk-cursor query orders by `id::text`** (string) but compares against a UUID column without explicit cast type alignment — `WHERE (transaction_date, id::text) > ($1, $2)` forces a sequential scan and can skip rows when `id::text` collation differs from PK ordering.

Additional warnings cover BoE CSV parser ambiguity, the empty-rates-payload edge case (BoE outage spoof), commission-processor SQL parameter ceiling, and worker-side fan-out behaviour.

## Critical Issues

### CR-01: SQL injection via `sql.raw` interpolation of `groupIds` / `regionIds`

**File:** `src/lib/analytics/queries/regions.ts:183,219`, `src/lib/analytics/queries/location-groups.ts:161`, `src/lib/analytics/queries/hotel-groups.ts:237`
**Issue:** Query helpers concatenate id strings into raw SQL via `sql.raw(\`(${ids.map((id) => \`'${id}'\`).join(",")})\`)`. There is no validation that `id` is a UUID. While these helpers are called from server actions that nominally pass UUIDs (e.g. via `fetchRegionDetail(regionIds, parsed)`), nothing in the call chain validates the shape before reaching the SQL builder — the page-level handlers parse arbitrary URL-supplied strings (`searchParams?.get("region")` → `parseIdParam`) and pass them straight through. A crafted query string like `region='/**/UNION/**/SELECT/**/...` reaches the raw SQL builder.

This is also a broken contract: the Drizzle `inArray()` / `sql.param()` patterns used elsewhere in the same files prove the parameterized path works.

**Fix:**
```ts
// regions.ts:183
const regionFilter = inArray(regions.id, regionIds);

// regions.ts:219
const locationIdsInRegion = sql`
  SELECT ${locationRegionMemberships.locationId}
  FROM ${locationRegionMemberships}
  WHERE ${inArray(locationRegionMemberships.regionId, regionIds)}
`;

// location-groups.ts:161
const groupFilter = inArray(locationGroups.id, groupIds);

// hotel-groups.ts:237 — same pattern
```

For the IN-list inside `locationGroupRoomsSubquery(sql\`IN ${groupIdList}\`, ...)`, change the helper to accept a `string[]` and use `sql.param(ids)::uuid[]` with `= ANY(...)` (mirroring `locationGroupKiosksSubquery`'s active-ids handling).

### CR-02: Hardcoded production admin email as fallback in FX alert paths

**File:** `src/inngest/functions/fx-rates-fetch-daily.ts:117`, `src/lib/sales/etl/azure-etl.ts:189`
**Issue:** Both cron paths fall back to a hardcoded literal `"vedant.kalbag@weknowgroup.com"` when `process.env.FX_ALERT_TO` is unset. This is:
1. A production secret committed to source.
2. A deployment footgun — if the env var is misset on a preview branch, alerts go to the prod admin's inbox.
3. A bus-factor risk — when the named admin leaves, every preview branch silently spams them until someone discovers the literal.

The repo has prior precedent for this exact mistake (see `CLAUDE.md` §"Prod admin password rotation" — emails routed by env not by literal).

**Fix:**
```ts
// Throw if missing rather than fallback
const to = process.env.FX_ALERT_TO;
if (!to) throw new Error("FX_ALERT_TO env var is required for fx_rate alerting");
// ... use `to`
```

Set `FX_ALERT_TO` in `.env.example` and Vercel project settings (preview + prod). The kind `fx_rate_stale` from azure-etl.ts must surface a hard config error rather than silently route to a personal inbox.

### CR-04: DST boundary off-by-one in `staleDays` arithmetic — silently lets stale rates pass the D-07 ceiling

**File:** `src/lib/fx/rate-lookup.ts:88`, `scripts/backfill-net-amount-gbp.ts:67-69`
**Issue:** `staleDays` is computed as `Math.floor((Date.parse(isoDate) - Date.parse(rateDate)) / MS_PER_DAY)` where `MS_PER_DAY = 86_400_000`. `Date.parse` of a bare `"YYYY-MM-DD"` string is parsed as UTC midnight. Across a UK DST clock change between `rateDate` and `isoDate`, the elapsed wall-clock interval is 23h or 25h, but `Date.parse` of a UTC-midnight string ignores zone — both endpoints are 00:00:00 UTC and the arithmetic returns the correct integer day-difference.

That part is fine on its own. The defect is at the consumer: D-07 is "more than 7 calendar days older" (CONTEXT.md). The current implementation rounds `Math.floor((delta_ms) / 86400000)`. If a future change ever feeds these inputs through a localized-Date intermediate (e.g. a `new Date(yyyy, mm-1, dd)` somewhere upstream), the floor + DST jitter produces a 6.96-day or 7.04-day boundary case that is silently miscompared against `> 7`. The same arithmetic appears in two places (rate-lookup.ts and backfill-net-amount-gbp.ts), increasing surface for drift.

More immediate concern: the lookup tests pin specific dates ("2026-05-15 = 7 days") but never exercise across a DST transition. The Apr→May 2026 fixtures all sit on the BST side; a Jan→Apr range would cross the GMT→BST boundary. Per RESEARCH Pitfall 7 the Postgres `date` arithmetic is the canonical path; the JS arithmetic was added because rate-lookup is sometimes called against a non-DB context (`if (currency === "GBP") return ...`). Recommend computing `staleDays` server-side (push the calc into the `lte()` SELECT) or using a pure-day-count helper that operates on `yyyy-mm-dd` strings without crossing through `Date`.

**Fix:**
```ts
// Pure string-day arithmetic — no Date, no DST exposure
function daysBetweenIso(isoFrom: string, isoTo: string): number {
  const [y1, m1, d1] = isoFrom.split("-").map(Number);
  const [y2, m2, d2] = isoTo.split("-").map(Number);
  const a = Date.UTC(y1, m1 - 1, d1);
  const b = Date.UTC(y2, m2 - 1, d2);
  return Math.floor((b - a) / 86_400_000);
}
const staleDays = daysBetweenIso(row.rateDate, isoDate);
```
Also extract this helper to a single location so the backfill script and rate-lookup share it. Add a unit test that picks dates straddling 27 Mar 2026 (GMT→BST) and 31 Oct 2026 (BST→GMT).

### CR-05: Backfill cursor uses string-collated `id::text` against a UUID PK — risks skipping rows + forces seq-scan

**File:** `scripts/backfill-net-amount-gbp.ts:138-142`
**Issue:** The chunk-cursor query is:
```sql
WHERE net_amount_gbp IS NULL
  AND (transaction_date, id::text) > ($1, $2)
ORDER BY transaction_date, id::text
```
Two problems:

1. **Type mismatch in tuple comparison.** `id::text` and `$2` (also text) compare lexicographically. UUIDs ordered as text are NOT identical to UUIDs ordered as `uuid` — the casts force Postgres to evaluate `id::text` for every row in the index range, defeating any planner use of the (transaction_date, id) index. On a 95k+-row backfill this scales linearly off the WAL and effectively becomes a seq-scan inside the long transaction. RESEARCH Pitfall 7 explicitly warned against locking patterns that hold an oversized transaction.

2. **Cursor advancement vs idempotency interaction.** `cursorId` is set from `rows[rows.length - 1].id` (already a text-cast id), but on the next chunk the WHERE compares `(date, id::text) > ...`. If two rows share the same `transaction_date` but their `id` text-collation order differs from the natural uuid-collation order at the chunk boundary, rows can be skipped or revisited. The `WHERE net_amount_gbp IS NULL` filter masks revisits (already stamped) but masks skips (still NULL) only for the next pass — they fall through and break migration 0048's NOT NULL flip pre-flight.

**Fix:** Drop the text cast and compare uuids directly:
```ts
// Drop the ::text casts. cursorId is already a string from the previous fetch
// — Postgres accepts a text-form uuid in $2 and casts it to uuid for the
// comparison if id is uuid.
`SELECT id::text AS id, currency, net_amount::text AS net_amount,
        transaction_date::text AS transaction_date
 FROM sales_records
 WHERE net_amount_gbp IS NULL
   AND (transaction_date, id) > ($1::date, $2::uuid)
 ORDER BY transaction_date, id
 LIMIT $3`
```
Adding `BEGIN; SET LOCAL statement_timeout = '0';` is also worth considering since the entire backfill currently runs in one transaction (`client.query("BEGIN")` at line 120, `COMMIT` at line 214) — if the table has 1M+ rows, this risks prolonged lock contention. Consider committing per-chunk instead of per-run, with the rate cache surviving across commits.

## Warnings

### WR-01: BoE CSV parser silently swallows `Number(",")` and similar truthy-empty cells

**File:** `src/lib/fx/boe-fetch.ts:120-128`
**Issue:** The cell-empty check is `if (!cell || cell === "") continue;`. After `cells = line.split(",").map((c) => c.trim())`, a cell containing only whitespace is already trimmed to `""`. But a cell containing the string `"NaN"` or `"-"` (BoE has historically used both for "not published") will pass the empty check and reach `Number("-")` → `NaN`, then fail `Number.isFinite(rate)` and throw. That's the right behaviour for explicit non-numeric strings, but the test fixture coverage only proves "blank" handling. The malformed-cell test uses `"not-a-number"` which is also caught — but `Number(",")` returns `NaN` and `Number(".")` returns `NaN`, both correctly thrown. Number(" ") returns 0 — also caught (positive). Number("") returns 0 — caught by the empty-string short-circuit.

The actual gap: `Number("0")` is finite and would parse to 0, then fail `ParsedRateSchema.parse` (rate must be positive). That throws a generic Zod error rather than a row-named one. Operator triage worsens.

**Fix:** Add a positive check in the row loop with a row-naming throw:
```ts
const rate = Number(cell);
if (!Number.isFinite(rate) || rate <= 0) {
  throw new Error(
    `BoE CSV invalid rate "${cell}" for series ${series} (${ccy}) on ${dateCell} (must be positive finite)`,
  );
}
```
Drop the redundant `ParsedRateSchema.parse` (already validated above) or keep it for type safety but acknowledge it'll never fire post-fix.

### WR-02: Empty BoE payload silently records `upserted=0` — operator cannot distinguish from real Sat/Sun no-publish

**File:** `src/inngest/functions/fx-rates-fetch-daily.ts:136-156`
**Issue:** Per the design (RESEARCH Pitfall 1), Sat/Sun/UK-bank-holiday produce empty CSVs and are NOT failures — the carry-forward at ETL time covers it. Implementation correctly returns `upserted=0` and writes the audit row. But `parseBoeCsv` returns `[]` for ANY of:
- A real Sat/Sun/holiday (intended).
- A BoE outage where the endpoint returns an empty 200 OK.
- A BoE schema change that breaks the header row (the parser throws in that case — covered).
- A future format where unknown-only series codes appear (parser silently skips per `BOE_SERIES_TO_CCY`).

Distinguishing 1 from 2 matters because case 2 is a stealth FX outage that won't surface until D-07's 7-day window expires and ETL starts hard-failing — by then operators have ~7 days of un-stamped sales rows.

**Fix:** When `rates.length === 0` AND the requested `isoDate` is a UK weekday that is not a UK bank holiday, log + emit a low-priority operator note (separate from `fx_rate_fetch_failed`). A simple `isUkBusinessDay(isoDate)` helper plus a `fx_rate_empty_publish_day` audit row is enough — operators can tail audit_logs and see "empty on Tuesday" as a real outage signal.

### WR-03: FX-rate gate in `azure-etl.ts` makes one DB roundtrip per `(currency, transactionDate)` — no batching

**File:** `src/lib/sales/etl/azure-etl.ts:160-204`
**Issue:** The defensive pre-check loops over `distinctPairs` and awaits `getRateForDate(...)` per pair sequentially (line 180). For a multi-region blob with 30 transaction-dates × 5 currencies = 150 sequential roundtrips before commit even starts. The same logic exists in `pipeline.ts:389-408` but uses an in-batch `Map<string, ...>` cache; the pre-check here doesn't share it.

This isn't a correctness bug, but it doubles ingest latency on large blobs and the pre-check happens AFTER `_stageImportForActor` already wrote staging rows — the latency directly extends the advisory-lock hold time.

**Fix:** Either:
1. Drop the pre-check entirely and rely on `pipeline.ts`'s in-loop check (the alert email loses the "first stale pair" naming but operators still get the alert from the next loop iteration); or
2. `Promise.all` the pair lookups since they're independent.

### WR-04: `comparison.ts:findSimilarLocations` — `notInArray` + `combineConditions` for HAVING is not parameter-safe

**File:** `src/lib/analytics/queries/comparison.ts:248-251`
**Issue:** The HAVING clause concatenates two SUM expressions with `revLow` and `revHigh` interpolated via Drizzle's tagged template — that's safe. But the `revLow`/`revHigh` themselves are derived from a SUM over the cohort, which in turn is filtered by `inArray(salesRecords.locationId, cohortLocationIds)`. If `cohortLocationIds` ever contains a non-UUID string (e.g. URL injection through `experimentCohorts.locationIds` JSONB), the inner query throws on the `inArray` parameter cast — but the THROWN error message bubbles up as "SQL error" without context, making operator triage hard.

Lower-priority than CR-01 because cohort IDs come from server-side seeded JSONB rows, but harden the entry point: validate that every id in `cohortLocationIds` matches `^[0-9a-f-]{36}$` before reaching the query builder.

### WR-05: `commission/processor.ts:234-237` — `sql.join` of `salesRecordIds` exceeds 65,535 bind-parameter ceiling on full-month recalcs

**File:** `src/lib/commission/processor.ts:234-237`
**Issue:** The "exclude this batch from cumulative" subquery is:
```sql
${salesRecords.id} NOT IN (${sql.join(salesRecordIds.map((id) => sql`${id}::uuid`), sql`, `)})
```
Each id becomes a bind parameter. The header comment at line 86 acknowledges Postgres's 65,535 ceiling and chunks the up-front fetch (`ID_CHUNK = 10_000`), but the cumulative-base query at line 234 receives the entire `salesRecordIds` list un-chunked. A `recalculateCommissions(lpId, month)` call on a heavy month (95k+ records) hits the bind-param ceiling and throws.

The pre-Phase-9.1 code may have had the same defect (commission-processor predates this phase), but the Phase 9.1 D-15 swap to `net_amount_gbp` puts new traffic through this exact path and amplifies the risk: the cumulative-base SUM is now the source of tier-bracket boundaries, so the bug surfaces as a wrong commission calculation when the query silently fails over a parameter-list overflow path.

**Fix:** Stage `salesRecordIds` into a temp table or use `WHERE NOT EXISTS (SELECT 1 FROM unnest($1::uuid[]) v WHERE v = sales_records.id)`:
```ts
sql`NOT (${salesRecords.id} = ANY(${sql.param(salesRecordIds)}::uuid[]))`
```

### WR-06: `azure-etl.ts:171-176` — fragile JSONB unpacking, missing-field renames silently produce NULL rows

**File:** `src/lib/sales/etl/azure-etl.ts:163-176`
**Issue:** The pre-check reads `parsed_row->'parsed'->>'currency'` and `parsed_row->'parsed'->>'transactionDate'`. The shape is dictated by `pipeline.ts:180-183`'s `StoredStagedRow` payload (parsed: ParsedSalesRow + resolution). If the parser ever renames `currency` → `currencyCode` (legitimate refactor), this query silently returns rows with `currency: null` and `transactionDate: null`, the loop at line 178 skips them via `if (!pair.currency || !pair.transactionDate) continue`, and the gate is a no-op — every blob passes regardless of FX rate freshness.

There is no test that asserts the gate fires when staleDays > 7 with a real (currency, date) pair stamped into staging. `tests/sales/pipeline-fx.integration.test.ts` exists but tests the in-pipeline gate; the azure-etl pre-check is a separate code path.

**Fix:** Either:
1. Type the JSONB destructure: cast `parsed_row->'parsed'` to a known shape with a defensive Zod schema in JS post-fetch.
2. Simplify the gate by dropping it (per WR-03) — the in-pipeline gate already enforces D-07 with the same hard-fail.

### WR-07: `inngest/fx-rates-fetch-daily.ts:148` — `String(r.rate)` for numeric(18,10) loses precision for currencies < 1 GBP

**File:** `src/inngest/functions/fx-rates-fetch-daily.ts:147-150`
**Issue:** The comment claims `String(r.rate)` preserves JPY-class precision because the parser already validates `r.rate` as a finite positive number. But JS Number is IEEE 754 double — for a rate like `212.9834567890` (10 significant figures), `String(212.9834567890)` returns "212.9834567890" only when the parsed value is exactly representable. BoE rates with 6 decimals (the published precision) round-trip cleanly through Number → String, but the schema column is `numeric(18,10)` which is future-headroom for KRW (~1500/GBP)/IDR (~19,000/GBP) where 6-decimal precision matters less but a 10-decimal spec might be added later. The fix is cheap: just push the original CSV cell string through verbatim instead of round-tripping through Number.

**Fix:** In `parseBoeCsv`, also store `rateRaw: cell` (the trimmed CSV cell string) on the parsed row. Use `r.rateRaw` (validated as `\d+\.\d+`) in the upsert instead of `String(r.rate)`.

### WR-08: `outlet-types/pipeline.ts:161` — orderBy SUM expression rebuilt unparameterized

**File:** `src/app/(app)/settings/outlet-types/pipeline.ts:161`
**Issue:**
```ts
.orderBy(desc(sql`COALESCE(SUM(${salesRecords.netAmountGbp}), 0)`));
```
This is a duplicate of the SELECT expression (line 143) and survives Postgres's ORDER BY semantics by re-aggregating — but Drizzle re-parameterizes both sites independently, so changing the FILTER clause on the SELECT (e.g. dropping the `FILTER (WHERE buildSalesTxnCondition())` for some operator-toggle reason) means the SELECT and ORDER BY disagree and rows sort by a different metric than what's returned. Less load-bearing today but a foot-gun for future maintainers.

**Fix:** Either alias the SELECT and reference the alias in ORDER BY (Drizzle's `.orderBy(desc(sql`revenue`))` on the alias name), or extract the SUM expression to a const SQL fragment and reuse.

### WR-09: `pivot-engine.ts:399-403` — `currency_key` filter for `booking_fee` is leaky

**File:** `src/lib/analytics/pivot-engine.ts:398-403`
**Issue:** When the value config field is `booking_fee`, the FILTER clause applied to currency_key resolution is `IS_FEE_RAW_SQL` (`is_weknow_fee = true`). Correct in principle: the currency_key tracks fee-cohort currencies. But the same SQL fragment is also generated when the field is `net_amount` and there's NO filter applied to currency_key. The actual emitted SQL becomes:
```sql
CASE WHEN COUNT(DISTINCT sales_records.currency) = 1
     THEN MIN(sales_records.currency)
     ELSE NULL END AS "currency_key_net_amount"
```
This counts currency over EVERY row (including reversal rows and fee rows), but `net_amount` SUM in saved pivots is currently raw native (no FILTER applied at line 359 `${v.aggregation.toUpperCase()}(COALESCE(${expr}, 0))`). Since SUM and currency_key disagree on which rows they're aggregating, a multi-currency-on-fee-rows-only cohort with all sales in GBP can produce currency_key=GBP (because COUNT(DISTINCT) is 1) while the SUM includes EUR fee rows that the renderer assumes are GBP. The wrong currency symbol gets rendered.

This is a subtle correctness issue masked by the fact that prod's `net_amount` pivots almost always include both fee and non-fee rows in mixed regions. The defect surfaces when a saved pivot filters down to a single fee-only cohort across two regions.

**Fix:** Mirror the SUM's filter on the currency_key resolver. Since the SUM has no filter for `net_amount`, the currency_key is also unfiltered — that's already the case. The bug is the asymmetric handling for `booking_fee`: the SUM expression at line 87 includes `(CASE WHEN ${IS_FEE_RAW_SQL} THEN ... ELSE 0 END)`, which sums 0 for non-fee rows but does NOT exclude them from the rowset. To make currency_key track exactly the same population the SUM "sees with non-zero contribution", emit:
```sql
CASE WHEN COUNT(DISTINCT sales_records.currency) FILTER (WHERE ${IS_FEE_RAW_SQL}) = 1
     THEN MIN(sales_records.currency) FILTER (WHERE ${IS_FEE_RAW_SQL})
     ELSE NULL END
```
The current code does this — but it should explicitly NOT apply the filter for `net_amount`. Add a unit test asserting this.
