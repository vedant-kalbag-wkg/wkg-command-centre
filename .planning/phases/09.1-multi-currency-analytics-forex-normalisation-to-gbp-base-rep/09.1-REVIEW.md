### Gap-closure quality assessment

The closures are mostly thorough — every prior BLOCKER has tests pinning the fix at the correct boundary (drizzle pg uuid cast for CR-01; new helper module for CR-04; integration-test cursor for CR-05; 70k-row real-DB drive for WR-05). The asymmetry comment in `pivot-engine.ts` is unusually well-written and includes a self-protecting test that scans the source for the WR-09 marker.

However, the gap-closure commits introduce two NEW defects that ship blocking-grade behaviour, plus four lower-severity issues:

1. **NEW BLOCKER**: `getFxAlertRecipient()` throw inside the cron's `catch` block masks the original BoE fetch error. The very purpose of the catch is "emit the alert, then re-throw the original error so Inngest counts the retry"; if `FX_ALERT_TO` is unset on a preview deploy, the helper's `throw new Error("FX_ALERT_TO env var is required...")` propagates instead, swallowing the BoE error entirely. Operators chasing a "BoE 503" outage instead see "FX_ALERT_TO env var is required" — wrong root cause and the alert email never fires.
2. **NEW BLOCKER**: `EmailTemplate` closed union in `src/inngest/events.ts:28` was NOT extended with `"plain-text"`, but `fx-rates-fetch-daily.ts:123` and `azure-etl.ts:196` emit `template: "plain-text"`. The events module's load-bearing contract — "closed unions catch typos at the call-site" — is now violated for the FX kinds. The runtime works only because `inngest.send` and `step.sendEvent` are loosely typed and the SUT casts via `unknown`.

The four warnings cover an unused import, a server-action defense-in-depth gap, a `_resend` cache singleton that survives `RESEND_API_KEY` rotation, and the pre-existing in-pipeline FX gate not deduped against the per-blob gate.

## Critical Issues

### CR-01 (NEW): `getFxAlertRecipient()` throw masks the original BoE error in the cron catch handler

**File:** `src/inngest/functions/fx-rates-fetch-daily.ts:113-132`, `src/lib/sales/etl/azure-etl.ts:186-207`
**Issue:** The cron's `catch (err)` block builds the alert payload object eagerly:

```ts
} catch (err) {
  alerted = true;
  const reason = err instanceof Error ? err.message : String(err);
  await args.step.sendEvent("emit-fx-fetch-failed", [
    {
      name: "email/send.requested",
      data: {
        kind: "fx_rate_fetch_failed",
        to: getFxAlertRecipient(),   // ← throws if FX_ALERT_TO unset
        ...
      },
    },
  ]);
  throw err;   // never reached when getFxAlertRecipient() threw
}
```

`getFxAlertRecipient()` is called in the argument-evaluation phase BEFORE `step.sendEvent` runs. If `FX_ALERT_TO` is unset (preview branch where the env var was forgotten, or staging where it's intentionally null), this evaluation throws `Error("FX_ALERT_TO env var is required for fx_rate alerting...")`. That throw bubbles up through the `catch` block and replaces the original `err` (BoE 503, network timeout, parse failure, whatever) — which Inngest then surfaces as the "real" failure reason, and the operator email is never sent.

This is exactly the failure mode the gap-closure plan called out as the prior CR-02 problem inverted: instead of "wrong recipient", it's now "no alert at all + wrong root cause in the Inngest dashboard". The end-state for the operator is strictly worse — at least the hardcoded literal alerted SOMEONE.

`azure-etl.ts:186-207` has the same defect: `getFxAlertRecipient()` is called inside the `await inngest.send(...)` argument BEFORE the `throw new Error("FX-02 stale-rate gate: ${reason}")` at line 207. If FX_ALERT_TO is unset, the per-blob stale-rate alert vanishes; the blob still fails (caught by the outer ETL try/catch), but the operator never sees `fx_rate_stale` and the staleness reason is lost.

**Fix:** Resolve the recipient ONCE at the top of `_handleFxRatesFetchDaily` (before the try/catch) so the missing-env-var throw fires deterministically at run-start, not when an alert is most needed:

```ts
export async function _handleFxRatesFetchDaily(args: {...}): Promise<...> {
  const isoDate = args.isoDate ?? todayIso();
  const alertRecipient = getFxAlertRecipient();   // throw at run-start, not in catch
  let alerted = false;
  ...
  } catch (err) {
    ...
    await args.step.sendEvent("emit-fx-fetch-failed", [{
      ...
      data: { ..., to: alertRecipient, ... },
    }]);
    throw err;   // now actually reached
  }
}
```

For `azure-etl.ts`, lift the recipient lookup to the top of `runAzureEtl` (alongside `containerName`) so a misconfigured deploy fails on the very first ETL invocation rather than silently dropping FX-stale alerts.

Add an integration test that drives `_handleFxRatesFetchDaily` with FX_ALERT_TO unset and asserts that (a) the helper throws BEFORE entering the BoE fetch step, and (b) the original BoE error message is preserved when FX_ALERT_TO is set and BoE returns 503.

### CR-02 (NEW): `EmailTemplate` closed union not extended with `"plain-text"` — wire-shape contract silently violated

**File:** `src/inngest/events.ts:28`, `src/inngest/functions/fx-rates-fetch-daily.ts:123`, `src/lib/sales/etl/azure-etl.ts:196`
**Issue:** `events.ts` documents the closed-union design intentionally:

```ts
// `kind` and `template` are closed unions (NO `| string` fallthrough) —
// this catches typos at the call-site. Phase 9 extends each union as it
// adds digest / kiosk_offline / report templates; the matching entry must
// also appear in send-email.ts's TEMPLATES dispatch table.
...
export type EmailTemplate = "password-changed" | "poc-underperformance";

export type EmailSendRequested = {
  name: "email/send.requested";
  data: {
    ...
    template: EmailTemplate;
    ...
  };
};
```

Phase 9.1 gap closure added a sentinel template literal `"plain-text"` (consumed in `send-email.ts:86`) but did NOT extend `EmailTemplate`. Both new emit sites use `template: "plain-text"` against a union that does not include it:

- `fx-rates-fetch-daily.ts:123` — `template: "plain-text"`
- `azure-etl.ts:196` — `template: "plain-text"`

The closed-union typo-catch contract is now silently broken for these kinds. The runtime "works" only because:
1. `inngest.send(...)` and `step.sendEvent(...)` accept loosely-typed events at runtime (no compile-time `EmailSendRequested` enforcement).
2. The SUT in `send-email.ts:115` casts via `as unknown as Parameters<typeof _handleSendEmail>[0]["event"]` — bypasses the union check.

Practical risk: a future call site that DOES type its emit through `EmailSendRequested` (e.g., a typed event-bus wrapper) will compile-error with `"plain-text" is not assignable to EmailTemplate`, and someone will "fix" it by stripping the type rather than adding the union member — at which point a typo like `template: "plian-text"` ships silently. The events.ts comment block's stated load-bearing invariant is "extends each union as it adds new templates; the matching entry must also appear in send-email.ts's TEMPLATES dispatch table" — Phase 9.1 violates the first half explicitly (and side-steps the second by adding a sentinel branch instead of a TEMPLATES entry).

**Fix:**

```ts
// src/inngest/events.ts
export type EmailTemplate =
  | "password-changed"
  | "poc-underperformance"
  | "plain-text";   // sentinel for hand-crafted text-only emails (FX alerts)
```

Update the events.ts comment block to document the sentinel convention: "templates ending in -text or named `plain-text` route through send-email.ts's `template === \"plain-text\"` branch and are dispatched by `kind` rather than by the React TEMPLATES table". Add a unit test that imports `EmailSendRequested` and constructs the FX alert payload with strict typing, asserting it compiles.

### WR-01: `regions.ts:31` imports `calculatePeriodChange` but never uses it (dead import)

**File:** `src/lib/analytics/queries/regions.ts:31`
**Issue:**

```ts
import { getPreviousPeriodDates, calculatePeriodChange } from "@/lib/analytics/metrics";
```

`calculatePeriodChange` appears only in this import line; `regions.ts` never calls it. Likely a leftover from a previous shape where `RegionData` carried a percent-delta. The neighbour `hotel-groups.ts:23` legitimately uses both imports; `regions.ts` should drop the unused one.

Build cleanliness — `tsconfig` is not configured to error on unused imports, so this slipped through; ESLint with `@typescript-eslint/no-unused-vars` would catch it. Risk if left: future maintainer assumes `revenueChange` is computed in `regions.ts` like in `hotel-groups.ts`, wires it through `RegionData`, then realises the import is decorative and the SQL doesn't actually return previous-period rows in a comparable shape.

**Fix:** Drop `calculatePeriodChange` from the import. If percent-change on regions becomes a deliberate add later, re-introduce alongside the SQL change.

### WR-02: Server actions don't validate `regionIds` / `groupIds` before passing to the SQL builder

**File:** `src/app/(app)/analytics/regions/actions.ts:24-31`, `src/app/(app)/analytics/hotel-groups/actions.ts:24-31`, `src/app/(app)/analytics/location-groups/actions.ts:24-31`
**Issue:** The CR-01 closure relies on drizzle's pg adapter throwing on the uuid cast as the actual security boundary. The defense-in-depth via `isUuid` filter happens on the CLIENT (`page.tsx`), which a malicious caller bypasses by POSTing directly to the server-action endpoint. Server actions accept `regionIds: string[]` and pass straight to `getRegionDetailCached(...)`.

The pg adapter throw IS sufficient to block injection (verified by `uuid-injection.integration.test.ts`), but:
1. The uuid cast error message bubbles up to the client as a generic 500 — operator support has no signal that someone is probing for SQLi.
2. If the SQL builder is ever changed to use a non-uuid type cast (e.g. text-array for a name-based filter), the silent-defense vanishes.

The `assertUuidArray` helper exists explicitly for this layer (`src/lib/uuid.ts:23-29`) and is not used anywhere on the server side.

**Fix:** Add `assertUuidArray(regionIds)` (and equivalents for groupIds) at the top of each server action. Throw before the cache wrapper and before any DB call. The unit test in `uuid-injection.integration.test.ts` should be updated to assert the throw fires AT THE SERVER-ACTION boundary, not at the SQL builder — that's the architectural intent.

### WR-03: `_resend` lazy singleton survives `RESEND_API_KEY` env-var rotation in long-running processes

**File:** `src/inngest/functions/send-email.ts:36-40`
**Issue:**

```ts
let _resend: Resend | null = null;
function getResend(): Resend {
  if (!_resend) _resend = new Resend(process.env.RESEND_API_KEY);
  return _resend;
}
```

`_resend` is initialised with the API key value at first call and cached for the lifetime of the Node process. If the API key is rotated in Vercel env vars, the running Inngest worker won't pick it up — every subsequent send fails 401 until the worker is redeployed. Vercel's serverless function lifetime mostly hides this, but Inngest function instances DO survive across many invocations on warm functions, and the gap-closure plan adds two new high-stakes alert paths (fx_rate_fetch_failed, fx_rate_stale) that can't afford silent 401s.

The `EMAIL_REPLY_TO` lookup at line 152 reads from `process.env` per-call (correct); the API key should match.

**Fix:** Read `RESEND_API_KEY` per call and pass to a fresh `new Resend(apiKey)` (the constructor is cheap — it's a JS class init, not a network call). If startup-cost matters, key the cache on the env-var value:

```ts
let _resend: Resend | null = null;
let _resendKey: string | undefined;
function getResend(): Resend {
  const apiKey = process.env.RESEND_API_KEY;
  if (_resend && _resendKey === apiKey) return _resend;
  _resend = new Resend(apiKey);
  _resendKey = apiKey;
  return _resend;
}
```

### WR-04: `azure-etl.ts` per-blob FX-stale pre-check duplicates the in-pipeline gate without sharing the rate cache

**File:** `src/lib/sales/etl/azure-etl.ts:160-209`
**Issue:** This was previously logged as WR-03 (latency) and WR-06 (JSONB unpacking) and remains unfixed. The pre-check loops `getRateForDate(...)` per `(currency, transactionDate)` pair sequentially before commit. `pipeline.ts` repeats the same check inside the commit transaction. Each call hits the database; neither path shares a per-batch cache.

The new `azure-etl.ts:186-209` `inngest.send(...)` event also includes `getFxAlertRecipient()` in argument-eval position (see CR-01 for the failure mode there) — both issues compound on the same code block.

Standalone severity for the duplicate-call concern: low (correctness is fine; latency doubles for large blobs). But the duplicate path is now responsible for the FX-stale alert email, which means the duplicate code is also a duplicate alert-emission risk — if the per-blob and in-pipeline gates ever drift on the staleDays threshold, operators get conflicting signals.

**Fix:** Either drop the per-blob pre-check and rely on `pipeline.ts`'s in-loop gate (the alert email loses the "first stale pair" naming, but operators still get the alert from the next loop iteration); or share a `Map<currency|date, RateLookupResult>` cache across both paths via a thin helper. Consolidate the alert-emission to one site so the two paths can't diverge on what they tell the operator.
