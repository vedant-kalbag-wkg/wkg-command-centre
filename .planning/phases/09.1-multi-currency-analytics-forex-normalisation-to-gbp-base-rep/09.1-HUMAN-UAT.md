## UAT run summary (2026-05-10, autonomous)

Two real Phase 9.1 defects surfaced in this UAT cycle and were fixed on this
branch before sign-off:

1. **BoE series codes** — 4 codes (THB/HKD/DKK/RUB) returned `HTTP 302 →
   ErrorPage`, poisoning every cron run. 11 `XUDLBK*` codes returned HTTP
   200 but were Effective Exchange Rate Indices, not GBP-spot rates,
   producing values 3-30× off real magnitudes (NOK 94 vs ~12, INR 301 vs
   ~110, ZAR 4.89 vs ~22, etc.). Phase 9.1 was shipping silently wrong
   `net_amount_gbp` for 21 of 26 currencies.

   Fix: `7560774 fix(09.1): correct BoE series codes`. Replaced BK codes
   with verified short-form codes where one exists; dropped CNY, INR, KRW,
   MXN, BRL, TRY, AED, ILS, PLN, HUF, THB, RUB (no working IADB spot
   series). 15 BoE-supported currencies + GBP — every code probed live on
   2026-05-07 with magnitudes inside realistic GBP-spot bands.

   Regression gate: `tests/lib/fx/series-codes-live.integration.test.ts`
   probes every series + asserts magnitude bounds (catches both 302 drift
   AND future ERI mis-mapping).

2. **`/admin/performance-alerts` SSR crash** — drizzle's `sql<Date | null>`
   template does NOT route aggregate-expression results through node-pg's
   column-level `timestamptz` parser. `MAX(exchange_rates.fetched_at)`
   returned the raw string, the page called `.getTime()` on it, and SSR
   threw `not a function` the moment any row existed in `exchange_rates`.
   The route 500'd as soon as the daily cron produced its first row,
   masking the stale-banner toggle UAT.

   Fix: `65ca116 fix(09.1): coerce aggregate timestamps to Date`. Added
   local `toDate(v: Date | string | null)` boundary helper, routed both
   aggregate-timestamp results through it.

### UAT caveats (require explicit operator decision before merge to main)

1. **FX scope reduced** — `BOE_SUPPORTED_CURRENCIES` shrank from 26 to 16
   currencies. Operators with sales in CNY, INR, KRW, MXN, BRL, TRY, AED,
   ILS, PLN, HUF, THB, or RUB will hit D-03 hard-fail at ETL ingest with
   `"currency not in BOE_SUPPORTED_CURRENCIES"`. This is **strictly safer**
   than the prior behaviour (silent 3-30× wrong `net_amount_gbp`), but it
   IS a deliverable change vs the original Phase 9.1 design contract.
   Operator must confirm before merging that the 12 dropped currencies
   are not in current production sales data — the auto-memory + STATE.md
   indicate all current sales (95k rows) are GBP-only, so this is
   currently low-risk, but a future Azure ETL run that ingests one of
   the dropped currencies would now hard-fail rather than silently
   corrupt.

2. **`analytics-currency-render` Test 1 deferred** — single-currency
   cohort (EUR-only region → €) requires multi-currency seed data not
   present in the preview Neon DB (all 95k sales records are GBP under
   the United Kingdom region). The renderer dispatch logic IS unit-tested
   in vitest; the live preview test for the GBP fallback path passed
   (Test 2 → £). The native-symbol render is operator-driven against a
   multi-currency seed dataset, which is out of scope for this autonomous
   UAT. Recommend running Test 1 against any future preview/staging
   environment that has non-GBP sales data.
