## Rate source & ingest

### Q1 — Where should the daily reference rate come from?

| Option | Description | Selected |
|---|---|---|
| ECB euro reference rates | Free, zero-auth, ~30 currencies. Pivots through EUR (triangulation). | |
| Bank of England daily spot | Free, zero-auth, native GBP base. No triangulation. Smaller coverage but covers our majors. | ✓ |
| NetSuite published rate | 1:1 reconciliation with NetSuite's books. Couples ETL to vendor auth. | |
| Defer to research | Researcher digs in first. | |

**User's choice:** Bank of England daily spot.
**Notes:** Native GBP base eliminates triangulation error (ECB rejected on this basis). NetSuite-as-source rejected because there's no current Finance reconciliation requirement worth the vendor-coupling cost.

### Q2 — How should the daily BoE rate fetch be scheduled and how does it order against the Azure sales ETL?

| Option | Description | Selected |
|---|---|---|
| Inngest cron, runs before sales ETL | New `fx-rates.fetch-daily` Inngest function, e.g. 06:00 UTC. Sales ETL becomes downstream. | ✓ |
| Inngest cron, independent of sales ETL | Decoupled failure domains. BoE outage doesn't block sales. | |
| Piggy-back on Azure ETL run | First step of azure-etl.ts ensures rate exists. Simplest schedule, couples failures. | |
| Vercel cron route | Vercel-native scheduling, doesn't require Inngest. | |

**User's choice:** Inngest cron, runs before sales ETL.
**Notes:** Reuses Phase 8/9 Inngest substrate. Sales ETL verifies rate row exists for `transaction_date` before stamping `net_amount_gbp`.

### Q3a — Currency coverage

| Option | Description | Selected |

## Missing-rate gap-fill

### Q4 — Routine non-publish dates (weekends, bank holidays)

| Option | Description | Selected |
|---|---|---|
| Carry-forward last published rate via lookup | exchange_rates only stores publish-day rows; lookup via `<= transaction_date`. Standard finance practice. | ✓ |
| Materialise carry-forward into exchange_rates | Cron writes daily; non-publish days copy previous business day. Trivial equality joins. Bigger table. | |
| Defer — pick at plan time | Either is fine. | |

**User's choice:** Carry-forward last published rate (via lookup, no materialisation).
**Notes:** Cron writes ~5 rows per currency per week. Lookup uses `WHERE rate_date <= transaction_date ORDER BY rate_date DESC LIMIT 1`.

### Q5 — Daily BoE fetch failure (network, BoE down, parse error)

| Option | Description | Selected |
|---|---|---|
| Block sales ingest until rate is present | Loudest signal. No NULL `*_gbp` columns ever exist. | |
| Ingest with carry-forward, alert ops | Carry-forward within bounded window; sales keep flowing during outages. | ✓ |
| Ingest with NULL `*_gbp`, patch in follow-up job | Backfill job patches once rates land. Analytics handles NULL. | |

**User's choice:** Ingest with carry-forward, alert ops.
**Notes:** Sales keep flowing during BoE outages — operationally critical; we can't block ingest on a third-party publisher.

### Q6a — Staleness ceiling

| Option | Description | Selected |
|---|---|---|
| 7 days | Long bank-holiday weekend + few days outage tolerance. Hard-fails after. | ✓ |
| 3 days | Tight. Fast ops attention. | |
| 14 days | Permissive. Higher tolerance for stale stamps. | |

**User's choice:** 7 days.
**Notes:** Beyond 7 days carry-forward, sales ETL hard-fails for that blob — loud signal that pipeline is genuinely broken, not just a long weekend.

### Q6b — Alert path

| Option | Description | Selected |
|---|---|---|

**User's choice:** Email admin via existing email_log substrate.
**Notes:** Two new email kinds: `fx_rate_fetch_failed` (cron-emitted on BoE error) and `fx_rate_stale` (ETL-emitted when 7-day ceiling exceeded).

## Companion column scope

### Q7 — How many GBP companion columns?

User initially asked for clarification on the question (didn't understand the schema framing). Clarification provided: walked through (a) what's currently on `sales_records` (`net_amount`, `vat_amount`, `currency`; no `gross_amount` since the 2026-04-24 NetSuite ETL rewrite dropped it), (b) what we're adding (a GBP-equivalent of each amount stamped at ingest), (c) the three options and trade-offs.

| Option | Description | Selected |
|---|---|---|
| A — net_amount_gbp only | Smallest migration. Solves the actual ranking bug. Matches issue #39 acceptance criteria. | ✓ |
| B — net + vat | Adds vat_amount_gbp. Cheap insurance for future cross-currency Finance reports. | |
| C — All three (ROADMAP literal) | Adds total_amount_gbp as derived denormalisation. Largest migration. Drift risk. | |

**User's choice:** A — `net_amount_gbp` only.
**Notes:** ROADMAP wording will be updated in this phase to reflect what actually ships (the original wording was aspirational; `gross_amount` being dropped in 2026-04-24 wasn't accounted for at roadmap-write time).

## Analytics UX continuity

### Q8 — pivot-engine swap shape

| Option | Description | Selected |
|---|---|---|
| Silently replace meaning — `net_amount` → GBP-normalised | Saved pivots auto-upgrade. Native pivot-accessibility lost. | |
| Add `net_amount_gbp` as new field, keep `net_amount` raw | Two fields. Footgun (raw cross-currency aggregate) preserved. | |

| **(User free-text)** Switch native vs GBP — note Sales = SUM(net_amount) WHERE NOT is_weknow_fee, Revenue = SUM(net_amount) WHERE is_weknow_fee | User wanted a switch, not a silent swap, and reminded that both Sales and Revenue modes aggregate `net_amount` (just with different `is_weknow_fee` filters). | (initial direction) |

**User's initial direction:** Native↔GBP switch + reminder that both Sales and Revenue modes aggregate `net_amount` differently filtered. Triggered follow-up.

### Q9 — Toggle scope (where it lives, what "native" means in mixed-currency cohorts)

User rejected the framing and clarified the underlying rule:

> "If the data being aggregated has multiple currencies, I want it all reported in GBP. If the data only has a single currency, then it is to be displayed in native currency. This is dependent on the data being selected — we don't need a switch for the user."

**Resolved rule:** Display follows data, no user-facing toggle. Single-currency cohort → native (with that currency's symbol). Multi-currency cohort → GBP (£). Per-kiosk drill-downs are single-currency by construction → native (matches existing Phase 9 contract).

### Q10 — Cross-cohort ranking when displays are native

| Option | Description | Selected |
|---|---|---|
| Always compute GBP underneath; display native when single; ranking always GBP | Every query returns both native + GBP + currency-key. Sort/rank uses GBP. | ✓ |
| Display drives compute; single-currency tables sort by native, multi by GBP | Simpler; cross-currency cohort comparison breaks. | |

**User's choice:** Always compute GBP underneath. Sorting/ranking always GBP. Display picks native when single-currency cohort, GBP when mixed.
**Notes:** Means a EUR-only region and a GBP-only region rank correctly against each other in the same view while each shows its own native total. Sorting is independent of display.
