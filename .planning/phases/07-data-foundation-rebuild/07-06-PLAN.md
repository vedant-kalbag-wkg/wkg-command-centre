<objective>
Correct the v2 data model so locations are keyed by **customer_code** (the
hotel account identifier — the per-hotel concept) and **outlet codes are
strictly a kiosk attribute** (the per-SSM identifier used in bookings).

The current schema mis-stores `outlet_code` on `locations` as the primary
identifier (NOT NULL, unique per region) — that conflates kiosk-level data
with hotel-level data. The Monday boards encode the correct shape:
`mirror3__1` ("Cust_cd (RPS)") on hotel boards mirrors the customer code
from the Assets board's `text9`, and each kiosk on Assets carries its own
`outlet_code1`. The Phase 7 re-scope is to align the database with this
domain model before the prod cutover.

**Hard constraint per operator:** RTL/Heathrow placeholder locations may
have `customer_code = NULL` — partial uniqueness only when populated.
</objective>

<context>
Discovered during Plan 07-05 UAT validation:
- 374 Live Estate hotels, 87.7% have `mirror3__1` populated (4-digit RPS codes)
- 30 of 84 Ready to Launch items have customer codes
- 12 of 53 Australia DCM items have customer codes (the live group is complete)
- 1 of 12 Heathrow Express items has customer codes (mostly empty)
- Multi-kiosk hotels show comma-duplicated codes ("2357, 2357") — same hotel = same account = single dedup'd code

Schema reality (already in place):
- `locations.customer_code` already exists at `src/db/schema.ts:166` as nullable text — never populated
- `salesRecords.customer_code` already exists at `src/db/schema.ts:744` — populated by CSV parser (`src/lib/csv/sales-csv.ts:235`)
- The dimension resolver in `src/lib/csv/dimension-resolver.ts` doesn't currently consult either

187 references to `locations.outletCode` across the codebase. Most are
analytics display labels and exclusion-pattern matching.
</context>
