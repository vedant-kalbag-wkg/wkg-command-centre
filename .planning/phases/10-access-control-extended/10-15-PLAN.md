## T1 — ability-eval gap on /locations/[id] for admin (root-cause investigation)

### Confirmed by reading source

**`src/lib/casl/ability.ts` has TWO independent short-circuits that grant `manage all`:**

```ts
// Line 34 — userType OR text-mirror == 'system'
if (userType === "system" || (u.role as string) === "system") {
  builder.can("manage", "all");
  return builder.build();
}

// Line 67 — ANY user_roles row points at a role with kind='system'
if (grants.some((g) => g.roleKind === "system")) {
  builder.can("manage", "all");
}
```

**For test admin (`admin@weknow.co`):**
- `user.userType` is `'internal'` per schema enum (`src/db/schema.ts:41` — `enum: ["internal", "external"]`, NO `"system"` value). Confirmed against `src/lib/auth/get-user-ctx.ts:31` which defaults to `"internal"`.
- `user.role` is text `'admin'` per `src/db/seed.ts:12` — `auth.api.createUser({ ..., role: "admin" })` writes `user.role='admin'` via better-auth.
- **Therefore line-34 short-circuit DOES NOT fire** (`"internal" !== "system"` AND `"admin" !== "system"`).

**The only path to `manage all` for admin is line 67 — `grants.some((g) => g.roleKind === 'system')`.**

That requires:
- A row in `user_roles` with `user_id = admin.id` AND `role_id = (SELECT id FROM roles WHERE name='admin')`.
- The `roles` row with `name='admin'` to have `kind='system'`. **Confirmed** by migration 0051:26 — `('admin', 'system', 'Admin', ...)`.

### Hypothesis (most likely): `admin@weknow.co` has NO `user_roles` row on the preview DB

Migration 0051 Delta 4 (lines 87-93) backfills:
```sql
INSERT INTO "user_roles" ("user_id", "role_id", "assigned_by")
  SELECT u.id, (SELECT id FROM "roles" WHERE name = 'admin'), NULL
    FROM "user" u
    WHERE u.role = 'admin'
  ON CONFLICT DO NOTHING;
```

This catches admins who existed BEFORE 0051 ran. But:
- `src/db/seed.ts` calls `auth.api.createUser({ ..., role: "admin" })` — better-auth's admin plugin writes `user.role='admin'` but does NOT insert into `user_roles`.
- If `admin@weknow.co` was (re-)created on the preview DB **after** 0051 ran (e.g. via `npm run db:seed` post-migration, or via the prod-admin-password-reset path that recreates the user record), the user has `user.role='admin'` text but **no `user_roles` row**.
- Both 10-14 SUMMARY metric (4/8 PASS) and 10-13-PARTIAL Run 4 logs corroborate: admin signs in successfully (Better Auth's `requireRole('admin')` reads `user.role` text and passes), navigates to /locations/[id] cleanly post-Plan-10-14, but the `<Can>` gate evaluates false — exactly the shape "session middleware sees admin, but the CASL builder can't find the bridge to `manage all`."

### Branch B (less likely): mis-assigned role

A `user_roles` row exists for admin but points at a non-system role (e.g. the seed accidentally assigned admin to `ops-it`). Diagnostic: `SELECT r.name, r.kind FROM user_roles ur JOIN roles r ON r.id = ur.role_id JOIN "user" u ON u.id = ur.user_id WHERE u.email = 'admin@weknow.co';`. If this returns rows but none have `kind='system'`, that's Branch B.

### Branch C (least likely): ability-builder bug

`user_roles` correct, but `buildAbility` somehow does not see the `kind='system'` grant. Possible causes: a transient DB-cache issue, the `react.cache` memoisation returning a stale Ability, or a subject/action-name mismatch between the `<Can I="merge" a="Location">` JSX literal and the ability internals. Diagnostic: a node-level repro (see T1 action).

**Do NOT edit ability.ts under Branch C without producing the node repro first** — Plan 10-04's CASL invariants forbid blind changes to the builder. AND the edit MUST carry the marker comment `// Plan 10-15 Branch C — <one-line root cause>` adjacent to the changed line, so the verify gate can detect the Branch C path deterministically.

### The canonical Radix interaction pattern

Replace:
```ts
await page.getByLabel(/role/i).selectOption({ label: "ops-it" });
```

With:
```ts
await page.getByLabel(/role/i).click();
await page.getByRole("option", { name: /ops.?it/i }).click();
```

Why this works:
- `getByLabel(/role/i)` resolves to the Radix SelectTrigger (Plan 10-14 added `aria-label="Role"`).
- `.click()` opens the Radix listbox (mounted in a portal).
- The Radix `<SelectItem>` components render as `role="option"` in the portal.
- `getByRole("option", { name: /ops.?it/i })` matches the option by its accessible name (the rendered text — `"Ops-IT (tier)"`).

**For role-editor.spec.ts lines 50-51** the same pattern applies, BUT note that line 50 `getByLabel(/action/i)` targets `ActionChips` (button chips, not a Radix Select) — see assumption #7. Apply the click+option-click pattern to line 51 (subject Radix Select); line 50 will still fail because there is no Action Select at all. **Document this in the spec edit** with an inline comment so future operators understand the partial fix.
