# Notifications Delivery Model — v1.1 NOTIF-01/02

## TL;DR Recommendation

**Email + deep-link only (Option 3).** Lean on EMAIL-04's Resend queue, drive every email back into the tool via deep links, defer the in-app notification centre to v1.2+ if real demand emerges. Subscriptions are per-kiosk follow + per-region (no per-group); throttling is a 5-min digest window keyed by `(userId, entityType)`.

## Options Considered

| Option | Schema cost | UI cost | Time-to-ship | UX quality |
|---|---|---|---|---|
| 1. Email-only | `notification_subscriptions` (1 table) | `/account/notifications` prefs page | ~3 days | OK — but emails dead-end if no link |
| 2. Hybrid (email + in-app centre) | `notifications` + `notification_subscriptions` + read-state | bell + dropdown + list page + poll/SSE + prefs page | ~8–10 days | Best, but overbuilt for 30 desk users |
| 3. **Email + deep-link** | `notification_subscriptions` (1 table) | prefs page + per-kiosk follow toggle | **~3–4 days** | Email is the surface, tool is the destination |

## Rationale

30 internal users at desks all day already live in Outlook/Gmail — that's the existing notification centre. Building a second one (bell, unread badge, polling/SSE, read-state sync between email and app) duplicates infra to chase a UX we don't have evidence anyone wants. Event volume is tens/day; an email digest with a "View kiosk →" link round-trips users into the tool exactly when they need to act, and costs us one table + one prefs page on top of work EMAIL-04 already does. If feedback later asks for in-app unread state, the `notifications` table is a strictly additive migration — no rework. Ship the simple thing; let real usage justify the bell.

## Subscription model

- **Per-kiosk follow** — star button on kiosk detail page (most granular, covers ad-hoc "watch this one rollout").
- **Per-region** — checkbox list on `/account/notifications` (covers Ops who own a geography).
- **NOT per-hotel-group** — adds a join dimension for marginal value; users wanting a group can star its kiosks or pick the region.
- **Admin offline alerts (NOTIF-02)** — implicit subscription for `role='admin'`, no opt-in toggle; opt-out via prefs page.

## Throttling rule

Single rule: **5-minute digest window, keyed by `(recipientUserId, entityType)`**. Cron runs every 5 min, drains pending events from `audit_logs` (where `field IN ('status','pipeline_stage')` and a matching subscription exists), groups them per recipient, sends one email per group. Rule covers both bursty bulk-updates (50 kiosks → 1 email listing all 50) and the offline-alert case (admin gets one email summarising N offline flips in the last 5 min). No instant push — 5 min is acceptable for an internal tool; SLA is not pager-grade.

## Schema sketch

```ts
// src/db/schema.ts — additive, no changes to audit_logs
export const notificationSubscriptions = pgTable("notification_subscriptions", {
  id: uuid("id").primaryKey().defaultRandom(),
  userId: text("user_id").notNull().references(() => user.id, { onDelete: "cascade" }),
  // 'kiosk' (entityId = kiosk uuid) | 'region' (entityId = region slug) | 'admin_offline' (entityId = '*')
  scope: text("scope").notNull(),
  entityId: text("entity_id").notNull(),
  // which audit field changes trigger: 'status' | 'pipeline_stage' | 'any'
  trigger: text("trigger").notNull().default("any"),
  createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull(),
}, (t) => ({
  uniq: uniqueIndex("notif_sub_uniq").on(t.userId, t.scope, t.entityId, t.trigger),
  byEntity: index("notif_sub_entity_idx").on(t.scope, t.entityId),
}));

// Cursor for the cron — last audit_log id processed per run.
export const notificationCursor = pgTable("notification_cursor", {
  id: text("id").primaryKey(), // singleton row: 'global'
  lastAuditLogId: uuid("last_audit_log_id"),
  lastRunAt: timestamp("last_run_at", { withTimezone: true }),
});
```

No `notifications` table in v1.1 — added when (and only when) we build the in-app centre.
