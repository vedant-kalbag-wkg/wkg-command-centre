# Email Job Queue + Cron — v1.1 EMAIL-04

## TL;DR Recommendation

**Inngest** (`inngest@4.2.6`). Free tier (100k executions/mo) covers our hundreds-of-emails/day load 100x over, ships retries with exponential backoff, dead-letter, dashboard UI, and cron — all over plain HTTPS to a Next.js route. No Redis, no DB queue table to babysit, no missed-window risk on Vercel cold starts (Inngest holds the schedule, then invokes us).

## Options Considered

| Option | Retry semantics | Observability | Cost @ volume | New infra dep |
|---|---|---|---|---|
| **Inngest** | Built-in: exponential backoff, configurable max attempts, per-step retry, DLQ | Hosted dashboard: runs, logs, replays, failure traces | $0 (≪100k execs/mo free) | SaaS account only; SDK is HTTP |
| Trigger.dev | Built-in retries + backoff, per-task config, DLQ | Hosted dashboard, run timeline | $0 free tier; heavier SDK, build step | SaaS account; CLI-driven deploy |
| Vercel Cron + DB queue (Drizzle `email_jobs`) | Hand-rolled (we write backoff, attempts, locking) | Hand-rolled (we build admin UI or read DB) | $0 (Pro plan already) | None — but writes ~200 LOC of queue code we own forever |
| BullMQ + Upstash Redis | Built-in (mature) | Bull-Board (self-host) | Upstash paid tier ~$10+/mo at any reliability | Redis (new infra) |

## Rationale

For a low-volume internal tool with no Redis and a small team, Inngest is the smallest total surface area. The DB-queue option looks "free" but we'd write polling, locking (`FOR UPDATE SKIP LOCKED`), backoff math, idempotency keys, and an operator UI — work that is exactly what Inngest gives us out of the box. Trigger.dev is comparable feature-wise but requires a build/deploy step per task definition; Inngest's "function = exported handler at `/api/inngest`" maps better to App Router. BullMQ is overkill at this volume and adds a paid Redis dependency. Vercel Cron alone (no Inngest) is fine for the daily digest *trigger*, but using it for transactional sends means we lose retry semantics — a Resend 5xx becomes a silent drop unless we build queue infra anyway.

Cold-start drift: Vercel Pro cron fires within the target minute, but the *function* still cold-starts; for transactional immediate sends a cold-start adds ~1s, acceptable. Inngest uses idempotency keys (`event.id` or `step.run` IDs) so duplicate cron firings don't double-send digests.

## Recommended schema sketch

We do NOT need an `email_jobs` table — Inngest holds queue state. We *do* keep a thin audit table for "what we sent" so operators can see history and dedupe digests:

```ts
// src/db/schema/email-log.ts
export const emailLog = pgTable('email_log', {
  id: uuid('id').primaryKey().defaultRandom(),
  kind: text('kind').notNull(), // 'password_reset' | 'invite' | 'digest_daily' | ...
  recipient: text('recipient').notNull(),
  resendMessageId: text('resend_message_id'), // from Resend API response
  inngestRunId: text('inngest_run_id'), // for cross-ref to Inngest dashboard
  status: text('status').notNull(), // 'sent' | 'failed' | 'bounced'
  lastError: text('last_error'),
  payloadHash: text('payload_hash'), // for idempotency on digests
  createdAt: timestamp('created_at').defaultNow().notNull(),
});
```

`payloadHash` (e.g. `sha256(kind + recipient + period_start)`) is the digest-idempotency guard: a unique index on `(kind, payloadHash)` makes a duplicate cron fire a no-op insert.

## Implementation note

Install:

```bash
npm install inngest@4.2.6 resend@6.12.2
```

Wire-up:

1. `src/inngest/client.ts` — `new Inngest({ id: 'wkg-kiosk-tool' })`.
2. `src/inngest/functions/send-email.ts` — `inngest.createFunction({ id, retries: 5 }, { event: 'email/send.requested' }, async ({ event, step }) => { await step.run('resend', () => resend.emails.send(...)); await step.run('log', () => db.insert(emailLog).values(...)); })`.
3. `src/inngest/functions/daily-digest.ts` — `inngest.createFunction({ id, retries: 2 }, { cron: 'TZ=Europe/London 0 7 * * *' }, async ({ step }) => { ... step.sendEvent for each recipient ... })`.
4. `src/app/api/inngest/route.ts` — `serve({ client: inngest, functions: [...] })` — single route, no `vercel.json` cron entries needed (Inngest schedules itself).
5. Set `INNGEST_EVENT_KEY` + `INNGEST_SIGNING_KEY` per Vercel env (preview alias + prod), bound via `vercel env add` like `BETTER_AUTH_URL`.

Skip `vercel.json` cron entirely; if v2 ever wants a pure-Vercel fallback, the daily-digest function's cron string is portable.
