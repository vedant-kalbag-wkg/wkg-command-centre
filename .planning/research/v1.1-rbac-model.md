# RBAC Permission Model — v1.1 AUTH-05/06

## TL;DR Recommendation

Adopt **CASL (`@casl/ability` 6.8.1 + `@casl/react` 6.0.0)** layered on top of the existing `userScopes` table. Roles + permission rules become DB-backed JSON, compiled into a CASL `Ability` per request. `userScopes` rows continue to drive `conditions` (region/group/location filters); a new `permissions` table drives `actions × subjects × fields`.

## Options Considered

| Option | Better Auth fit | Admin-UI ergonomics | Field redaction | Migration cost |
|---|---|---|---|---|
| Flat tiers + JSONB override | Trivial (no plugin) | Poor — bespoke UI per field, no schema | Manual per-field code (status quo) | Lowest, but doesn't solve AUTH-06 |
| **CASL** | Trivial — build `Ability` in `getUserCtx` | **Strong** — rules are JSON, round-trip to DB | **Native** — `fields` + dot-paths + `*` wildcards | Low — wraps existing `redactSensitiveFields` |
| Casbin | OK but heavy — model files awkward over DB | Weak — policy DSL hostile to non-devs | Possible via custom matcher, not idiomatic | Medium-high |
| accesscontrol-js | OK | Mediocre, attribute filters are flat | OK but glob-only, last release stale (2+ yrs) | Low but dying lib |
| Custom `can()` | Trivial | Worst — every new role = code change | Hand-rolled (status quo) | Zero, but blocks AUTH-05 |

## Rationale

CASL is the only option that gives **runtime-configurable rules** (rules are plain JSON arrays — store them, edit them in an admin form, hydrate them per session) **and** native field-level + conditional permissions, which directly maps to the four real-world cases in scope. `userScopes` becomes the source of `conditions` (e.g. `{ regionId: { $in: [...] } }`); we don't replace it. Bundle is ~6KB gz for `@casl/ability`, ~2KB for `@casl/react` — fine for client gating in the admin UI and field-level UI redaction. Casbin's policy DSL is a non-starter for a non-engineer admin form; accesscontrol-js is unmaintained; custom code re-creates CASL badly and locks AUTH-06 behind a deploy.

## Permission model sketch

Rule rows in a new `role_permissions` table (`roleId, action, subject, fields jsonb, conditions jsonb`) compile into:

```ts
// "Ops can edit kiosk.pipeline_stage but not kiosk.banking_details"
[
  { action: 'read',   subject: 'Kiosk' },
  { action: 'update', subject: 'Kiosk', fields: ['pipelineStage', 'hardware.*'] },
  { action: 'read',   subject: 'Kiosk', fields: ['bankingDetails'], inverted: true },
]
// regional scope from userScopes:
// + conditions: { regionId: { $in: scopeRegionIds } }
```

`ability.can('update', kiosk, 'bankingDetails')` → false. `permittedFieldsOf(ability, 'read', kiosk)` replaces `redactSensitiveFields` — same shape, rules-driven.

## Implementation note

- Install: `npm i @casl/ability@^6.8.1 @casl/react@^6.0.0`
- Integration point: extend `src/lib/auth/get-user-ctx.ts` — after Better Auth's `getSession`, load `role_permissions` for the user's role(s), `userScopes` for conditions, build with `new AbilityBuilder(createMongoAbility)`, attach to `UserCtx.ability`. No Better Auth plugin needed; this is a pure post-session derivation, so no conflict with the existing invite/session-cookie flow.
- Replace `canAccessSensitiveFields` / `redactSensitiveFields` callers with `ability.can(...)` and `permittedFieldsOf(ability, 'read', subject)`; keep the function signatures during migration so existing callers are a one-line swap.
- Admin UI (AUTH-05): a roles editor that writes `role_permissions` rows — no code deploy required to add a "Read-only-but-can-see-banking" role.
