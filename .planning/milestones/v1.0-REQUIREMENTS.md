# Requirements: Kiosk Management Platform

**Defined:** 2026-03-18
**Core Value:** Operations and IT teams can accurately track, plan, and report on every kiosk deployment across all regions from a single tool that models the business's actual data structure.

## v1 Requirements

### Authentication & Access Control

- [x] **AUTH-01**: User can sign up and log in with email and password
- [x] **AUTH-02**: User session persists across browser refresh
- [x] **AUTH-03**: User can reset password via email link
- [x] **AUTH-04**: Admin can create and manage user accounts
- [x] **AUTH-05**: Sensitive fields (banking details, contracts) are restricted to authorized roles only

### Kiosk Data Model

- [x] **KIOSK-01**: User can create a kiosk record with all fields (kiosk ID, outlet code, customer codes, hardware details, software version, CMS config status, installation date, deployment phase tags, maintenance fee, free trial status/end date, region/location group)
- [x] **KIOSK-02**: User can view, edit, and delete kiosk records
- [x] **KIOSK-03**: Kiosk has a status from a configurable lifecycle pipeline (default: Prospect → On Hold → Delivered to Region → Awaiting Configuration → Configured → Ready to Launch → Live → Offline → Decommissioned)
- [x] **KIOSK-04**: Admin can add, reorder, rename, and remove lifecycle stages
- [x] **KIOSK-05**: User can assign a kiosk to a venue and reassign it to a different venue
- [x] **KIOSK-06**: System tracks full assignment history per kiosk (which venues, date ranges, reason for move)

### Location Data Model

- [x] **LOC-01**: User can create a location (hotel/venue) record with all fields (name, address, lat/long, star rating, room count, key contacts, hotel group, sourced-by)
- [x] **LOC-02**: User can view, edit, and delete location records
- [x] **LOC-03**: User can attach contracts to a location with structured fields (start date, end date, value, terms) and file uploads (PDF/docs)
- [x] **LOC-04**: User can store banking details on a location record (restricted to authorized roles)
- [x] **LOC-05**: User can view all kiosks currently and historically assigned to a location

### Table View

- [x] **VIEW-01**: User can view kiosks and locations in a filterable, sortable table (the default interface)
- [x] **VIEW-02**: User can group table records by any field (status, region, hotel group, deployment phase, etc.)
- [x] **VIEW-03**: User can show/hide columns in the table
- [x] **VIEW-04**: User can save a custom view configuration (filters, grouping, visible columns, sort order) with a name
- [x] **VIEW-05**: User can load, update, and delete saved views

### Kanban View

- [x] **KANBAN-01**: User can view kiosks as cards on a Kanban board grouped by status
- [x] **KANBAN-02**: User can drag a kiosk card between status columns to update its status
- [x] **KANBAN-03**: User can group the Kanban board by other fields (region, hotel group, etc.)

### Gantt View

- [x] **GANTT-01**: User can view deployment timelines on a Gantt chart (kiosk/venue scheduled stages over time)
- [x] **GANTT-02**: User can view regional rollout plans as grouped Gantt bars
- [x] **GANTT-03**: User can set and view milestones (contract signing, go-live targets, review dates)
- [x] **GANTT-04**: User can assign resources (team members) to deployment tasks and view allocation

### Calendar View

- [x] **CAL-01**: User can view deployments, milestones, and deadlines on a calendar
- [x] **CAL-02**: User can filter the calendar by region, status, or hotel group

### Bulk Operations & Export

- [x] **BULK-01**: User can select multiple kiosk or location records and bulk-edit shared fields
- [x] **BULK-02**: User can export filtered table data to CSV or Excel

### Audit Log

- [x] **AUDIT-01**: System logs every change to kiosk and location records (who, what field, old value, new value, when)
- [x] **AUDIT-02**: User can view the audit log for a specific kiosk or location record
- [x] **AUDIT-03**: Admin can view the global audit log with filters (by user, entity, date range)

### Reporting & Dashboard

- [x] **REPORT-01**: User can view a dashboard with fleet health overview (total kiosks by status, pipeline breakdown, key metrics) — delivered off-GSD via PR #23 + analytics-audit arc
- [x] **REPORT-02**: User can view time-series charts (total kiosks live per month, new activations per month, growth trends) — delivered off-GSD (Trend Builder, Maturity dashboard)
- [x] **REPORT-03**: User can drill down from summary → hotel → individual kiosk in reports — delivered off-GSD (Region selector → hotel-group breakdown → outlet → kiosk)
- [x] **REPORT-04**: User can filter reports by region, deployment phase, hotel group, date range, and other fields — delivered off-GSD (global FilterBar, audit-fix Phase 3 wiring)

### Data Migration

- [x] **MIGR-01**: Admin can trigger a Monday.com data import that maps Monday.com board columns to kiosk/location fields
- [x] **MIGR-02**: Migration supports dry-run mode (preview imported data before committing)
- [x] **MIGR-03**: Migration handles pagination and rate limits for 1,000+ records

### Data Migration — Import Quality & Correctness (Phase 4.1)

- [~] **MIGR-04**: KioskId derived from "Region" column value + outlet code (e.g. "London-ABC123"), not from Monday.com group name — **superseded**: Phase 4.1 implementation uses Asset ID (Monday `item.name`) as `kiosks.kioskId`; region is captured via the kiosk's location FK. The original requirement was based on a misreading of the Monday data model. Kept here for traceability — no follow-up planned.
- [x] **MIGR-05**: "Assets" column (hardware ID/serial number) imported as kiosk `hardwareSerialNumber`, unique per kiosk — `scripts/import-from-monday.ts` line 277 sets `hardwareSerialNumber = item.name` from the Monday Assets board
- [x] **MIGR-06**: CMS Config status imported correctly from Monday.com status column (preserving actual label, not raw JSON) — `getColumnText(item, "status_1")` extracts the label string
- [ ] **MIGR-07**: Kiosk notes contain only genuinely relevant notes — unmapped location-targeted fields must not be dumped into kiosk notes
- [ ] **MIGR-08**: Key contacts import distinguishes hotel key contact name from WeKnow internal POC ("Key Contact" column = internal POC)
- [ ] **MIGR-09**: Hotels with same name but different `[outlet_code]` suffixes merged into one location with separate kiosks per outlet code — partially addressed via `formatHotelDisplayName` display-only suffix strip (audit-fix 4.7); full bulk merge tracked under Phase 6 (D8 multi-POS site merge, items 5.5-5.7)
- [x] **MIGR-10**: Hardware assets/kiosks imported first from board `1426737864`, hotel data imported separately
- [x] **MIGR-11**: Location schema extended with `region`, `locationGroup`, `internalPoc` (WeKnow internal POC), and `status` fields — verified in `src/db/schema.ts`: `internalPocId` (line 191), `locationGroup` (line 190), `status` (line 192); region via `primaryRegionId` FK (migration 0022)

### Data Migration — Table Display Fixes (Phase 4.1)

- [x] **MIGR-12**: Kiosk table displays only relevant columns by default: Asset (hardware serial number), outlet code, venue, region, pipeline stage, CMS config status, install date
- [x] **MIGR-13**: Location table displays all hotel metadata: name, hotel group, star rating, rooms, # kiosks, address, sourced by, status, maintenance fee, customer code, key contact name, region, location group, internal POC (key contact)

### Data Migration — Products & Kiosk Groups (Phase 4.1)

- [x] **MIGR-14**: Product management moved to a dedicated Products tab in the sidebar (not embedded within hotel/location detail) — `/app/(app)/products/` route exists with master catalog view
- [x] **MIGR-15**: Kiosk Groups tab with data imported from Monday.com board `1466686598` — separate entity for grouping kiosks

## v2 Requirements

### Access Control (Extended)

- **AUTH-V2-01**: Role-based access control with configurable Ops, IT, and Read-only tiers
- **AUTH-V2-02**: Admin can define custom roles with granular permissions

### Reporting (Extended)

- **REPORT-V2-01**: User can schedule automated reports delivered via email
- **REPORT-V2-02**: User can create and save custom report templates
- **REPORT-V2-03**: Analytics treatment of `freeTrialEndDate` (kiosks during free-trial period flagged in revenue rollups; trial-vs-paid revenue separation) — explicitly deferred from v1.0 per audit-fix D11. Pickup tied to the broader maintenance-fee recurring-revenue work when that lands. See `tasks/todo.md` §7.11 for the original context.

### Views (Extended)

- **VIEW-V2-01**: Map view showing kiosk locations on an interactive map using lat/long data

### Notifications

- **NOTIF-V2-01**: User receives notifications for status changes on kiosks they manage
- **NOTIF-V2-02**: Admin receives alerts for kiosks going offline

### Email Infrastructure (carry-over from v1.0 milestone close, 2026-04-28)

- **EMAIL-V2-01**: Transactional email provider integration. **Resend** chosen as primary (EU region, best Next.js DX, free tier covers volume); **Brevo** documented as fallback (not implemented). Replaces `nodemailer.createTransport` SMTP path in `src/lib/email.ts`. Forgot-password / invite / external-invite templates remain — only the transport changes. Includes SPF/DKIM/DMARC setup on the chosen sending domain (`weknowgroup.com` or `weknow.co`) and Vercel env wiring for `RESEND_API_KEY` + `EMAIL_FROM`. Implicitly fixes the silent-fail prod issue where forgot-password works in code but never delivers.
- **EMAIL-V2-02**: Self-serve change-password from `/account/security` while signed in. Wraps Better Auth `authClient.changePassword({ currentPassword, newPassword })`. Sends a "password was changed" confirmation email via the V2-EMAIL-01 substrate.
- **EMAIL-V2-03**: Forgot-password end-to-end deliverability UAT against prod once V2-EMAIL-01 lands (invite a throwaway user, click link, set password, sign in). Bundles with V2-EMAIL-01.
- **EMAIL-V2-04**: Transactional alerts substrate — shared `sendTransactional({ template, to, data })` helper, persisted `email_jobs` queue table with retry + audit_log, Vercel Cron worker. Lands before NOTIF-V2-01/V2-02 and REPORT-V2-01 so they share retry/template/audit-log plumbing instead of each reinventing it.

### Data Quality (carried over from v1.0 Phase 6 close, 2026-04-28)

- **DQ-V2-01**: Address-data-quality cleanup for the 61 active locations still missing `latitude`/`longitude` (BOTH_BLANK + NO_MONDAY rows from `scripts/probe-monday-vs-db-addresses.ts`). Hand-edit Monday hotel-board items, re-run `enrich-locations-from-monday.ts`, then `/settings/geocoding` Apply with skip-existing.
- **DQ-V2-02**: Cluster 10 — `0Y` Clayton London Wall has wrong sibling-copied address (currently shows Maldron Shoreditch's Paul Street address; correct is 16-22 Copthall Avenue, EC2R 7DA). Hand-edit + re-geocode that one row + audit-log.
- **DQ-V2-03**: Triage the 60 NO_MONDAY active locations — link to Monday, archive, or accept as legitimate non-Monday rows.

### Data Model (carried over from v1.0 Phase 6 close, 2026-04-28)

- **DM-V2-01**: Audit + collapse same-name active location pairs per the user directive "no two separate locations with the same name". 19 distinct hotel names currently have 2+ active rows (e.g. Residence Inn by Marriott Kensington has 8). Two new pairs (Sheraton Heathrow SSM, Radisson Blu Edwardian SSM) are direct consequences of Wave 1 renames and should be collapsed early. Decision needed: collapse-all-same-name vs keep-as-multi-kiosk-per-site (the multi-kiosk interpretation was the v1.0 default). See `tasks/v2-carryover-from-v1-phase-6.md` § V2-DM-01 for full reasoning.

### Testing & Tooling (carried over from v1.0 Phase 6 close)

- **TEST-V2-01**: Add single-pair fixture to `tests/scripts/multi-pos-merge.integration.test.ts` to catch the inArray() / raw-SQL ANY-array-binding bug class. The original raw-SQL `ANY(${ids}::uuid[])` failed on 1-element arrays under node-postgres; fix landed in commit b58a70b but no regression test was added.
- **TEST-V2-02**: Staging orphan-rate baseline measurement (Phase 6.7 follow-up). Prod baseline filled (11/36 = 30.56% on 2026-04-28); staging measurement still placeholder.
- **MONDAY-V2-01**: Drift detection / bidirectional Monday sync. Current enrich script only writes to NULL DB fields. As Monday gets edited, drift accumulates. Either extend with `--overwrite-stale` flag, build /settings admin UI for drift review, or schedule cron that surfaces drift.
- **REF-V2-01**: Analytics dashboards — migrate `useEffect → loadData()` pattern off `react-hooks/set-state-in-effect`. Repeats across every dashboard; bundle with broader RSC-first refactor.

## Out of Scope

| Feature | Reason |
|---------|--------|
| SSO/OAuth login | Email/password sufficient for v1; low user count doesn't justify SSO complexity |
| Mobile native app | Web-first; browser works on mobile devices |
| Real-time collaboration | No concurrent editing requirement for this use case |
| IoT/telemetry monitoring | Kiosk health monitoring is a separate system |
| Billing/invoicing | Handled in separate financial systems |
| External customer portal | Internal tool only |
| Real-time chat | Not relevant to asset management workflows |
